# Mac 当基站：价签一上电就自己拿到时间 + 天气

## 💥 2026-10-02 晚 4："刷了两次" —— 是我那句 `stop()` 引出的**跨线程竞态**（已修）

用户日志里开机 35 秒后：

```
Guru Meditation Error: Core 0 panic'ed (StoreProhibited). Exception was unhandled.
EXCVADDR: 0x00000000                       ← 往 0 地址写
Backtrace: 0x401e8930 0x400e1d7d 0x400e1ffe 0x400df812 0x40127645 0x40127ccc …
Rebooting…
```

用 addr2line 配合当次编译的 ELF 解出来：

| 地址 | 符号 |
|---|---|
| 0x401e8930 | `std::_Rb_tree_insert_and_rebalance`（std::map 插入） |
| 0x400e1ffe | `_Rb_tree<…, BLEAdvertisedDevice*>…` |
| 0x400df812 | **`BLEDevice::gapEventHandler`** |
| 0x40127645 | `btc_gap_ble_cb_to_app`（Bluedroid 的 BTC 线程） |

也就是：**崩在"扫描结果那张 map 的插入"上**。而第二次刷屏是**后果** —— ESP32 自己重启，
基站重新开机后又把时间/天气/城市名/纪念日/预警整包推了一遍，价签就只能再刷一次。

### 根因（读 core 源码 + 反汇编都对上了）

`~/Library/Arduino15/packages/esp32/hardware/esp32/3.3.11/libraries/BLE/src/BLEScan.cpp`：

```cpp
// BTC 线程里，往 map 插设备 —— **没有锁**
pScan->m_scanResults.m_vectorAdvertisedDevices.insert(…);

// 主任务里，删掉每个设备再清表
void BLEScan::clearResults() { for (auto _dev : …) delete _dev.second; …clear(); }

// start() 本身就带"清上一轮"的语义（is_continue=false）
if (!is_continue) { for (auto _dev : …) delete _dev.second; …clear(); }
```

原来的代码在 `scan->start(6,false)` 返回后**又手动 `clearResults()`** —— 平时安全，因为扫满
6 秒后 DISC_COMPLETE 早把事件排完了。但我加了"扫到就 `stop()`"之后：`stop()` 一给信号量，
`start()` 立刻返回，**BTC 线程这会儿还在处理回调、后面还排着 DISC 事件**，主循环就开始
`clearResults()` → **两个线程同时改同一张 map** → 内部指针写坏 → `StoreProhibited`。

### 修法

1. **删掉那句手动 `clearResults()`** —— 它本来就是多余的（`start(…, false)` 里的 `false`
   就是"清掉上一轮"，库在开始扫之前自己清，同一线程、安全）。让库自己去管那张表，
   我们一个字节都不碰。
2. 保留"扫到就 `stop()`"（省 5 秒），并在两处都写上"**绝不能再从别的任务里 clearResults()**"。

### 还没解决的一半：基站重启 = 价签重刷

基站判断"价签刚上电"的依据是**自己**第一次看到它（`tagPresent` 从 false 变 true），
所以**基站自己重启时也会误判**，于是把整包静态配置重推一遍。要根治得让价签报一个
"我是第几次开机 / 开机多久了"的标记（它的连接通知里现在只有配置字节），
基站据此区分"价签真重启"和"我自己重启"。这条先记进 backlog。

## 🧹 2026-10-02 晚 3：开机刷太多次 —— 合并刷新窗口（A）+ 没数据先别连（B）

用户："价签开机刷的次数太多了，有没有办法精简。"

**先数清楚**：基站 build-23 开机那一轮一共写了 5 条命令，而固件**每条命令都会立刻
整页重画 + 全刷 16 秒**（标志在开始重画时就被清掉，刷新又阻塞十几秒，所以后面的命令
一律变成"下一次重画"）：

| 时刻 | 命令 | 为什么要发 | 刷了几次 |
|---|---|---|---|
| 18s | `0x79` 城市名 | 基站刚重启，`citySent` 是内存里的空串 | 1 |
| 18s | `0x7A` 纪念日 + `0x7B` 续传 | 基站刚重启，`memoSent` 是 false | 2 |
| 78s | `0x20` 时间+天气 | 第一份数据到手 | 1 |
| 79s | `0x7C` 天气预警 | 预警和时间分开发的 | 1 |

**合计 5 次全刷 ≈ 80 秒在闪**，其中前 3 次纯粹为了两条**永远不会变的静态配置**。

### A. 固件（build 72）：合并刷新窗口

命令不再"立刻画"，而是把预约时间推到 `now + 2 秒`（`gui_request_redraw()`）；
poll 里到点才画（`(int32_t)(zk_tick_ms() - s_gui_due_ms) >= 0`，用减法比较防绕圈）。
2 秒内有新命令就一直往后推 —— **一次连接里连发的几条并成一次全刷**。
代价：屏上更新最多晚 2 秒。

### B. 基站（build 24）：手里没有有用数据就先别连

原来"价签一出现就强制连一次"（为了验证链路），可那时 WiFi/HTTP 还没成 —— 连上去
只能发城市名/纪念日。现在：**没时间、没天气 → 这轮不连**（`haveUsable`），等第一份
数据到手再连，静态配置跟着一起带上。留了兜底：价签出现后最多等 **60 秒**
（`TAG_FIRST_WAIT_MS`）还是连一次，免得中继和 Open-Meteo 同时不通时什么都不做。

### 🐛 顺手修的一个真 bug（同属 B）：开机后 60 秒内一次都不取数

```c
static unsigned long lastFetchTryMs = 0;                     /* 初值 0 */
if ((needWeather || needTime) &&
    (millis() - lastFetchTryMs) > FETCH_FAIL_BACKOFF_MS)     /* > 60000 */
```

初值 0 + "距上次尝试超过 60 秒" = **开机后 60 秒内永远不满足**，于是第一份数据
必然落在 61~71 秒 —— 翻历史日志（build-11/15/17/20/22/23）全是这个数。价签 8 秒就
出现了，却要干等一分钟。改成第一次立刻取（`lastFetchTryMs == 0` 视为"从来没试过"）。

### 预期效果

| | 开机刷几次 | 屏上正确要多久 |
|---|---|---|
| 改之前（build-23 + build-71） | **5 次** ≈ 80 秒 | ~90 秒（数据 61s 才到） |
| 改之后（build-24 + build-72） | **1 次** ≈ 16 秒 | ~30 秒 |

**验收**：`bash status.sh` 里那行「**画过 N 次**」—— 开机后读一次，应该是 1。

### ⏱️ "时间和天气为啥要那么久" —— 耗时拆解（build-24 加了每步毫秒计时）

**取数本身只要 1~2 毫秒**（局域网中继，实测 `curl -w %{time_total}` 三次：1.1 / 1.4 / 1.8 ms）。
慢的全是别的东西，按开机顺序：

| 段 | 耗时 | 出处 |
|---|---|---|
| setup 里等 USB 串口 | 1.2 s | `delay(1200)` |
| WiFi 关联 | 2~3 s（信号差时几十秒） | 日志 1s → 3s |
| **取时间 + 天气** | **1~2 ms** | 中继在局域网，本机 HTTP |
| 扫到价签 | 6 s（窗口写死 `SCAN_SECONDS=6`） | 日志 3s 开始扫、8s 才"命中" |
| BLE 连接 | **~8 s** | 日志 9s「连接中」→ 17s「连上了」（**可疑，正常应 <1 s**） |
| MTU + 写命令 | ~2 s | 日志 17s → 19s |
| 写完驻留收通知 | 1.5 s | `NOTIFY_DWELL_MS` |
| 价签合并窗口 | 2 s | build 72 |
| **面板整页全刷** | **16~17 s** | BUSY 85000 次 ≈ 17 s（物理时间） |

→ 插电到屏上正确 ≈ **40 秒**（改之前还有那个 60 秒 bug，所以是 ~90 秒）。

**为什么加了计时**：以前日志只有"秒"级时间戳，"几毫秒的取数"和"8 秒的连接过程"
长得一模一样 —— 只能猜。现在每一步都打毫秒数：

```
→ 命中价签：ZK42V-EPD  rssi=-68  addr=…（扫描开始后 5013 毫秒扫到）
连上了（BLE 连接本身用了 8021 毫秒）
MTU 协商后 = 247（一次能发 244 字节，耗时 312 毫秒）
命令发完（从连上到发完这一串：1830 毫秒）
已断开（本次连接总耗时 10180 毫秒）
```

**下一步能砍哪里**（等画像出来再定）：
1. **扫描 6 秒**：`scan->start(6, false)` 会把窗口跑满，其实扫到价签就能 `stop()` 提前退出。
   但日志显示"扫到"本身就要 5 秒 —— 活跃扫描 + 100ms 广播间隔，正常应该 **0.5 秒内**。
   **怀疑**（还没证据）是 ESP32 的 WiFi/BLE 共存抢射频（代码里早有注释提到
   "WiFi 会掉一下再自己回来（信号弱 + BLE 扫描抢射频）"）。画像会给出证据。
2. **BLE 连接 8 秒**：同上，正常应该 <1 秒。先看画像里 `connectTimeout` 自己占多少。
3. **面板全刷 16 秒**：这是墨水屏的物理时间，只能靠**局刷**（1~2 秒），而局刷参数一直
   没啃下来（backlog 第 5 条）。这是唯一真正的大头。

### 📊 画像实测（2026-10-02 20:56 那一轮 build-24 开机日志）

```

[5s]  天气源 = 局域网中继 25.0℃ 小雨   ← 数据到手（改之前是 61s）

[12s] 价签出现了 → 本轮强制校时        ← ⚠ 扫到只用了 1.1 秒，却等到 6 秒窗口跑满才返回
[13s] 连上了（BLE 连接本身用了 1168 毫秒）
```

结论（都有数字，不是猜的）：

| 段 | 实测 | 说明 |
|---|---|---|
| 取数 | **~0.1 秒**（1~2 ms） | 中继在局域网 |
| 扫描 | **1.1 秒扫到，但白等 5 秒** | 窗口跑满 → **已改成扫到就 `stop()`** |
| BLE 连接 | **1.17 秒**（后续几轮 0.26~0.41 秒） | 老日志里那个"8 秒"没再现，是当时射频/HTTP 抢出来的 |
| 写 5 条命令 | **0.30 秒** | 合并窗口之后只换 1 次全刷 |
| 面板全刷 | 16 秒 | 物理时间 |

后续几轮扫描都是 **17 / 29 / 48 毫秒**就扫到 —— 所以"扫到慢"只在开机第一次
（BLE 刚起来 + WiFi 刚关联），之后就快了。

**同时抓到我自己新引入的一个 bug**：`firstDone = everSynced || …` 写反了 —— 第一次
连完之后恒为真，于是之后每一轮（19s / 32s / 45s）都连上去、发现没东西要发再断开
（日志里 25s、38s 那两次"本次连接总耗时 2878 毫秒"的空连接）。已改回
`!everSynced && (haveUsable || waitExpire)`。

**两处都修完的预期**：扫到即停省 ~5 秒、空连接不再发生 →
插电到屏上正确从 ~40 秒降到 **~26 秒**。

## 🚨 2026-10-02 晚 2：ESP32 手写的 JSON 查找**没跳过冒号后的空格**（我的 bug）

实机（基站 build-23 + 中继）：

```
[BASE 71s] 天气源 = **局域网中继** 26.0℃ 小雨
[BASE 71s]   ⚠ 预警 橙色预警 到 （中继一并带上来的）      ← 名字和到期时间都是空的！
```

**数字全对、字符串全空**，差别就在一个空格：Python 的 `json.dumps` 默认输出
`"atype": "暴雨"`（冒号后带空格），而基站里 `findJsonNumber` 我写了"跳过空格"，
`findJsonString` 却写成了直接匹配 `"atype":"` —— 匹配不上就返回 false。
后果很隐蔽：**天气照常刷，只是预警画不出来**，不看串口发现不了。

两边都修了：

1. **中继改紧凑 JSON**（`separators=(",", ":")`）—— 这条**不用重刷基站就生效**
   （老解析器本来就认紧凑写法），代价是少几个字节。
2. **基站的 `findJsonString` 改成跳空格**（跟 `findJsonNumber` 一个写法：找到 key →
   跳空格 → 看是不是引号 → 不是就继续往下找）。
3. **基站加了自检**：`alert>0` 却读不到 `atype` 时，串口直接把报文前 120 字节打出来。
4. **补了一个能在电脑上跑的自测**：`esp32/tests/test_json_fields.py`
   —— 它**从 .ino 里抠出这几个函数**（不复制、不会脱节），配上极小的 Arduino
   `String` 替身，把真实报文喂进去：

```bash
python3 esp32/tests/test_json_fields.py                                   # 现在这份
ZK_INO=/tmp/old.ino python3 esp32/tests/test_json_fields.py               # 改之前那份 → 会红
```

拿改之前的 `.ino` 跑，正好复现实机现象（`alevel ✅` / `atype ❌ aend ❌`）—— 说明这个
测试真能抓住它。教训：**手写解析器 vs 真实报文，这种假设应该先在电脑上验，别烧到板子上试。**

## ✅ 2026-10-02 晚：中继顺带取**天气预警**，价签表头会显示（build 71 / 基站 build-23）

用户："手机上是局地雷暴雨而且有暴雨警报，中继获取的是小雨。"

两件事分开看：

1. **和风的实况文字本来就是"小雨"** —— 那是我们那个坐标（22.7809,113.8861 = 光明区）
   的观测/格点值；手机顶部那句"局地雷暴雨"来自**预警 + 雷达**，是另一个产品。
2. 手机挂的那条**暴雨警报**，和风有单独接口，用户的账号也开了 → 那就取回来、画上去。

```
和风 /weatheralert/v1/current ──(NAS 上的 wx-relay.py)──> 基站读 JSON
        ──(BLE 0x7C <级别> <类型名>)──> 价签表头：那格"天气文字"改画预警名
```

**⚠ 老接口已下架**：`/v7/warning/now` 现在直接回 `403 Deprecated`。新的是
`GET /weatheralert/v1/current/{纬度}/{经度}` ——**纬度在前**（`/v7/weather/now`
反过来是"经度,纬度"，和风自己都不统一）。

中继的 JSON 现在多四个**平铺**字段（不是嵌套对象，ESP32 那边是手写字符串查找，
嵌套的 `code` 会和实况的 `code` 撞车）：

```json
{"code":4,"temp":28,"text":"小雨","src":"qweather","obs":"…",
 "alert":3,"alevel":3,"atype":"暴雨","aend":"2026-10-03T18:34+08:00"}
```

| 字段 | 含义 |
|---|---|
| `alert` | 生效中的预警**条数**（0/缺省 = 没有） |
| `alevel` | 最严重那条的级别：1白 2蓝 3黄 4橙 5红（和风的 `color.code`） |
| `atype` | 类型名（暴雨 / 雷电 / 雷雨大风 / 台风 …） |
| `aend` | 到期时间（ISO 串，本地时间） |

两个基站都能发；三个工具都能看：

```bash
curl -s http://192.168.100.221:8788/wx                     # 中继看到了什么
python3 wx-compare.py --qweather-host … --qweather-jwt-key ed25519-private.pem \
        --qweather-kid … --qweather-sub … --qweather-dev-id …   # 逐条预警列出来
python3 ../firmware/tools/gui_preview.py 1 1790937600 /tmp/a.png 8 3970 349 0 6 28 深圳 '' '' 3 暴雨
```

价签侧（build 71）把表头那格"天气文字"换成预警名：级别 ≥3（黄/橙/红）画**红**、
1~2（白/蓝）画**黑** —— 三色屏只有黑/白/红。预警没了会专门发一条 `7C 00` 清掉。
字模只认 `tools/gen_font.py` 的 `ALERT_CHARS`（60 字）；"雷雨大风"实际画"雷雨大"
（那格就 3 个字的宽度）。详见 `outputs/firmware/docs/feature-backlog.md` 第 4 节。

### 为什么 ESP32 要自己签（以及它到底支不支持）

* **要**：JWT 的 `iat/exp` 用的是"现在几点"，而且 token 15 分钟就过期 ——
  要是让 Mac 签好再传，就得**Mac 常开**；而我们的基站是那台常开的 ESP32。
* **⚠ 但**：**ESP32 core 3.3.11 的预编译库里没有 Ed25519** —— 头文件里有
  `PSA_ALG_PURE_EDDSA` 的定义，但 sdkconfig 里只有 `CONFIG_MBEDTLS_ECP_DP_CURVE25519_ENABLED`
  （那是 X25519 密钥交换，不是 Ed25519），`libmbedcrypto.a` 里也搜不到 edwards/ed25519
  符号。实机一跑就是 `PSA 导入私钥失败：-135`（INVALID_ARGUMENT）。
  **教训：`#include` 有定义 ≠ 实现被编进去；"能编译链接"不等于"运行期支持"。**
* **所以自带一份 Ed25519**：公有领域的 **TweetNaCl**（`tweetnacl.c/.h`，
  https://tweetnacl.cr.yp.to/ 20140427 版，放在 sketch 目录里一起编译），
  只给它加了一个函数 `crypto_sign_seed_keypair()`（用固定 seed 推密钥对，
  原版只有随机版）。
  **验证过才敢用**：同一个 seed 推出来的公钥、以及照固件格式签出的签名，
  与 OpenSSL **逐字节一致**（Ed25519 是确定性签名，这样就等价于"验签通过"）。
  成本：整机 1,794,199 → **1,806,335 B**（约 +12KB）。
* **JWT 要用时间**：所以固件**总是先用 Open-Meteo（纯 HTTP）把 HTTP Date 头拿到手**，
  再签 JWT 去请求和风 —— 免得"要签名得先有时间、要时间得先能请求"的鸡生蛋问题。

### 跟 API key 比，好在哪

| | API key | JWT |
|---|---|---|
| 泄露后果 | 永久可用（直到你去控制台吊销） | **15 分钟就过期** |
| 出现在哪 | 在 URL 里（`?key=`）→ 会被代理/日志记下来 ⚠ | 在请求头里，且每次都是新的 |
| 轮换 | 换 key 要改所有客户端 | 换密钥对只影响自己 |

> 两种都支持：**填了 JWT 三项就优先用 JWT**，没填就退回 API key，再没有就用 Open-Meteo。
> 私钥文件（`qweather-ed25519.pem`）别进 git、别乱发。

## ⚡ 2026-10-01 又更新（build 67）：纪念日提醒（生日高亮）

### ⚠ 基站侧的一个硬限制：一次写不能超过 `MTU-3` 字节（build-9 修）

实机踩到的：ESP32 基站发 27 字节的纪念日命令时**卡了 40 秒然后失败**，屏上一直没框。
原因是 **ESP32 的 BLE MTU 默认只有 23**（ATT 一次只能发 20 字节），超了 Bluedroid 会
自动改用"长写（prepare/execute write）"，而价签的 GATT 不支持这条路径。

两处改动（基站代码里已经做好了）：

1. **命令分片**：长文案切成 ≤15 字节的段（`7A` 起头 + `7B` 续传），按 UTF-8 字符边界切。
2. **MTU 协商**：连上就 `client->setMTU(247)`（价签支持到 244）。谈成了以后一次能发
   244 字节；谈不成也没关系，分片那套兜着。

> 教训：**凡是往价签写超过 20 字节的东西，要么先协商 MTU，要么自己分片。**
> （城市名 7 字节、时间+天气 10 字节都在 20 以内，所以以前一直没暴露这个问题。）

日历翻到某个纪念日所在的月份时：**那天套一个黑框** + 在 **1 号左边那片空白里框出
祝福语**（空白不够就退到最后一行右边，再不够就只圈日子、不压字）。生日按"月日"重复，
所以每年那个月都会亮。

* Mac：`./run.sh sync --tz 8 --memo "10-05=付婧文生日快乐！"`（`--memo off` 清掉）
* ESP32：`#define MEMO_MON 10 / MEMO_DAY 5 / MEMO_TEXT "付婧文生日快乐！"`

⚠ **文案只能用固件字模里有的字**（`tools/gen_font.py` 的 `MEMO_CHARS`）。MCU 上没法现
栅格化汉字，认不出的字会被静默跳过（框照画、字少几个）。要换文案就先往那张表加字、
重编固件 —— 这也是目前唯一"要改固件才能换内容"的地方。

表头温度后面会写**经纬度所在地的城市名**（"多云 26°C 深圳"）。固件加了一条
`0x79 SET_CITY <utf8>`，**城市名由基站发**（基站才知道自己的坐标）：

* Mac：`./run.sh sync --city 深圳`（默认就是深圳；空串 = 不显示）

不做逆地理编码（免得再依赖一个外部接口）—— **换 `--lat/--lon` 时记得顺手改 `--city`**。

## ⚡ 2026-10-01 更新（用户提的：推天气时把时间一起带上）

**改了什么**：基站现在**每次推天气都把时间放同一条命令里**（`0x20` 的合并格式
`20 <utc4> <tz> <mode> [wx] [temp]`），所以每次推天气都顺便对一次表 ——
以前只有"刚上电 / 每天一次"才校时，两次之间的钟没人管。

配套三件事：

1. **模式字节发 0 = 保持当前页**（build 60 固件新增）。基站不知道用户在看哪一页
   （日历 / 时钟 / 推的图），发 1 会把页面顶掉；`0` 就是"只对表、别动页面"。
   Mac 版：`watch` 默认用 0（`--no-keep-mode` 可改回按 `--mode` 切页）。
2. **时间戳在写下去的前一刻才取**。以前 `now = int(time.time())` 在取天气之前就取了，
   取天气（HTTP）+ 连蓝牙要几秒~几十秒，等于把旧时刻写进价签。
   ESP32 版用 `epochNow()` = 上次拿到的 epoch + `millis()` 走掉的秒数，随时补到当前。
3. **ESP32 多了个旋钮 `PUSH_EVERY_MS`**（默认 0 = 关）：设成 `15*60*1000UL` 就是
   "不管有没有变化，每 15 分钟推一次（时间 + 当前天气一起带）"。

### ⚠ 关于"屏上时分比 Mac 慢几分钟"—— 那不是钟慢

用户 2026-10-01 看到"Mac 12:28、屏上 12:26"，怀疑推的时间是旧的。实测原因不是这个：

* 固件算"现在几点"= `推来的时间戳 + (单调时基 - 收命令那一刻)`（`zk_epd_svc.c` 里
  `cur = s_ts + el`），**推来的时间旧几秒也会自己补上** —— 只要时基准（build 59 起就准了）。
* 真正的原因是**日历页只在「换天」和「收到命令」时重画**：
  `if (s_need_gui) 重画; else if (日历) redraw = (换天); else redraw = (换分钟)`。
  所以屏上那个时分**只在每次推送的那一刻是对的**，之后一直停在原地，直到下一条命令。
  用户看到的 12:25 → 12:26 → 12:30 就是这么跳的（每次推送跳一下）。

**想让那个时分一直新，只有三条路**（都有代价）：

| 做法 | 屏上时分最多旧 | 代价 |
|---|---|---|
| 什么都不改（默认） | 上次推送的时间（可能几十分钟） | 无。日期/换天/农历都是准的 |
| ESP32 `PUSH_EVERY_MS = 15*60*1000UL`（或 Mac `--weather-interval 900`） | 15 分钟 | 每 15 分钟一次整屏全刷（约 8 秒真人时间），电池要算账 |
| 价签切**时钟模式**（网页「时钟模式」） | ~1 分钟 | 每分钟一次整屏全刷，**1440 次/天**，只适合当桌面钟 |

> 4.2 寸三色屏没有便宜的"只刷那一小块"（局刷已判定"可行但暂不做"，见
> `firmware/docs/feature-backlog.md`），所以这里没有第四种便宜办法。

## 1. 结论

**可以，而且不用改固件、不用传图。**

原因就在协议的方向上：价签固件（build 21 起）跑的是 tsl0922/EPD-nRF5 那套网页协议，
**价签是从机**（GATT server，`zk_ble.c` 里 `s_adv_time.duration = 0` = 一直广播、
断线后立刻重新广播），**手机/电脑才是主机**。网页那条路就是我们常见的"手机当基站"。

所以"用 Mac 模仿基站"= 让 Mac 当 BLE central：

```
价签上电 → 一直广播 ZK42V-EPD
                ↓  （Mac 扫到）
        Mac 连上去 → 发 0x20（UTC 秒 + 时区 + 模式）
                ↓
        价签 s_need_gui=1 → 自己画整页农历月历 → 写屏（约 16 秒）
        （再发 0x71 天气码+温度 → 表头出现图标 + 温度）
        Mac 断开 → 价签继续广播，下次上电再来一遍
```

关键点：**日历页是固件自己画的**（`Src/img/zkgui.c`），基站只喂"现在几点"和"什么天气"，
所以整条链路上没有 400×300 位图要传，除了写几个字节不需要 MTU 协商、不需要 RLE。

这也正好补上 HANDOFF 第 8 节第 1 条想要的效果（"装电池就显示日历"），
而且**不用碰 flash**：代价是得有个一直开着的 central（这台 Mac / 树莓派 / NAS 都行）。
两种做法的取舍见本文最后一节。

### 2.4 默认坐标（深圳公明广场）是怎么定的

不是随手估的，两条独立来源对上：

1. **OSM（Overpass API）** 在深圳 22.70~22.90 / 113.80~114.00 范围里搜名字含「公明广场」的节点/建筑，返回 8 条：
   `公明广场 lat=22.780875 lon=113.886101`（3 条同名、彼此差 2 米以内）、
   以及 `公明广场地铁站 ①/②`（22.7804~22.7808 / 113.8865~113.8874）——都在 20 米内。
   → 取广场本体 **`22.7809, 113.8861`**。
2. **Open-Meteo 地理编码**「公明」→ `22.78743, 113.88246`（公明街道中心，离广场约 1km）；
   把这一点丢给 BigDataCloud 反查，行政区划是 `中华人民共和国 / 广东省 / 深圳市 / 光明区 / 公明街道` ✅

天气数据是网格化的（Open-Meteo 会吸附到最近的网格点，上面那次是 22.8119/113.9063，约 3km 外），
所以广场中心和街道中心那 1km 的差别对天气没有意义；取广场本体只是为了让"默认值"能对得上地名。

换地方（比如价签搬到别处）就直接改命令行的 `--lat/--lon`，
或者按城市名查坐标：`https://geocoding-api.open-meteo.com/v1/search?name=杭州&count=1&language=zh`。

## 3. 怎么用（都能直接粘）

在 Terminal 里跑（`#` 开头的行可以一起粘，**行尾的注释别粘**，会被当成参数）：

```bash
cd /Users/mac/Documents/Codex/2026-09-15/a/outputs/ble-base

# ① 建环境（只需一次；需要联网装 bleak）。venv 已经建好了，这步可跳过
sh setup.sh

# ② 先扫一眼，确认 Mac 能看见价签。第一次会弹「Terminal 想使用蓝牙」→ 允许
./run.sh probe

# ③ 同步一次：校时 + 发天气（价签会整页重画，约 16 秒）
#    坐标默认就是深圳公明广场；换地方加 --lat xx --lon yy
./run.sh sync --tz 8

# ④ 基站模式：常驻，价签一上电就自动同步
./run.sh watch --tz 8 --log /tmp/zk-base.log
```

`probe` 正常长这样（`<== 价签` 那行就是它）：

```
[11:01:30] 扫到 2 个设备：
[11:01:30]   rssi=  -48  C75FC89D-F1A8-5498-8CCC-CC9841A8365C  'ZK42V-EPD'  ('62750001-d828-918d-fb46-b6c11c675aec',)  <== 价签
```

`sync` 正常长这样（这是 11:03 那次实机日志）：

```
[11:03:57]   → 时间：UTC 1790737436 + 时区8h → 价签应显示 2026-09-30 11:03:56，模式=1（日历）  载荷=20 6a bc 7c 1c 08 01
[11:03:57]   ← 价签：'t=1790766236'
[11:03:59]   → 天气：阴 26℃（Open-Meteo WMO=3 风速=5.2km/h）  载荷=71 03 1a
[11:03:59]   ← 价签：'wx=3 t=26'
```

（价签回的那串 `t=` 是**已经加过时区**的当地时间戳：1790766236 − 1790737436 = 28800 = 8 小时，
所以这个数能直接当"屏上显示的时刻"来对账。）

## 4. 为什么不能"每 30 秒同步一次"

固件 `zk_epd_svc.c` 第 930 行那段：

* 日历模式：**只有换天**（`cur/86400 != s_drawn_day`）才自己重画；
* 但 `0x20` / `0x71` / `0x72` / `0x70` 任何一条都会置 `s_need_gui = 1` → **立刻整页重画**；
* 一次整页 = 写 400×300 三色双平面 + 刷新，**约 16 秒**（build 22~46 的日志里一直这个量级）。

这是 2×CR2450 供电的价签，所以脚本按"少刷"来设计：

| 触发 | 默认 | 说明 |
|---|---|---|
| 价签**重新出现**（刚上电/刚换电池） | 立刻 | 这时价签里时间是空的，非发不可 |
| 时间 | 每 24 小时 | 用 `--time-interval` 改 |
| 天气 | 每 6 小时检查，**值变了才发** | 用 `--weather-interval` 改；白天升温降温会触发几次全刷 |

想让它更省：固件侧加一条"0x71 的值没变就不重画"（HANDOFF 第 8 节第 2 条里那个建议），
那就是改 `case 0x71` 里加个比对 —— 需要改固件、重新刷机，不急可以以后做。

### 4.1 已知的小浪费：一次同步会刷两屏

11:03 那次 `status` 里 `画过 2 次`，原因很具体：固件对**每一条**命令都置 `s_need_gui`，
而我们发了两条（`0x20` 时间、`0x71` 天气）→ 两轮"画图 + 刷新"。

脚本已经先改了一版（**先把天气取好再连**，两条命令挨着发，少 2 秒中间等待），
但只要还是两条命令，就可能还是两次画。要彻底变成一次，得动固件，两个改法：

1. **把天气塞进 `0x20`**（推荐，改动最小）：`20 <utc4> <tz> <mode> [wx] [temp]`，
   len>7 才解析天气 —— 网页只发 6 字节，行为完全不变，向后兼容。
   这样"校时 + 天气"是一条 GATT 写、一次画、一次刷新。
2. **在 `zk_epd_svc_poll` 里做合并**：`s_need_gui` 置上以后先等 ~300 ms 再画，
   期间来的命令自动并进去（顺便也治了网页那边连点两下的情况）。

两条都是十几行的改动，改完跑一遍 11 套离线自测 + 刷 APP 段就能验。

## 5. 开机自动跑（两条路）

1. **登录项（推荐，最省事）**：`系统设置 → 通用 → 登录项 → 加号`，
   直接选这个目录里的 `watch-on-air.command`（里面就是 `run.sh watch --tz 8 …`，
   想改城市/频率就改那几行参数；`probe-on-air.command` 是"只扫一次"的调试版）。
   为什么这样能行：终端窗口里的进程**继承 Terminal 的蓝牙授权**，不会碰到 TCC 的坑。
2. **LaunchAgent**：`~/Library/LaunchAgents/com.zk42v.base.plist` + `launchctl bootstrap gui/$(id -u) …`。
   坑在于 LaunchAgent 拉起来的进程**不是** Terminal 的子进程，TCC 会给它一个独立的（很可能是
   没弹窗、直接拒绝的）授权，实测常见的表现就是 `state=3 unauthorized`。
   要走这条路得把脚本包成带 `NSBluetoothAlwaysUsageDescription` 的 .app。

另外提醒：Mac 睡眠时 BLE 扫描是停的（`watch` 进程会被挂起）。
要么在「系统设置 → 锁定屏幕」里勾上"显示器关闭时防止自动进入睡眠"，
要么拿树莓派/NAS 当常驻基站（同一份脚本，Linux 上装 `bluez` 走 D-Bus，不用改代码）。

## 6. 和"把时间写进 flash"比

| | Mac 当基站（本文） | 时间持久化（HANDOFF 第 8 节第 1 条） |
|---|---|---|
| 要改固件吗 | 不用 | 要（往 `0x0107E000` 那颗空扇区写，还要读回来画） |
| 断网/没基站时 | 时间从上次同步开始走，久了会偏 | 时间一直准（走自己的 RTC tick） |
| 天气 | 能自动刷新 | 还是要外部喂（板子上没有温度传感器） |
| 风险 | 零（只发命令） | 动 flash 分区，得先拿出厂备份确认整颗是 `0xFF` |

两条可以并存：先把基站跑起来（立刻能用、还能自动刷天气），
以后再补 flash 持久化当"没基站时的兜底"。

验过了：

1. ✅ Mac 扫得到 `ZK42V-EPD` 并连上（`probe` + 实机 `watch`）。
2. ✅ `0x20` / `0x71` 都进了固件（调试块 `命令收到 2 条` / `天气收到 1 次` / `t=` 回报）。
3. ✅ 固件确实为这些命令画了页（`画过 2 次`、`模式=日历`、时间与时区都对）。

还差：

1. ⏳ **眼看屏**：日期/农历/天气图标是不是都对（`status` 工具对其中一次刷新报了
   "BUSY 轮询数太小、可能没做全刷"，需要人眼确认一下，见 2.2）。
2. ⏳ **断电重来一次**：拔电池/碰 RST，看 `watch` 是不是几秒内自己接上（上面那次其实验了，

3. ⏳ 要不要把 4.1 那个"一条命令同时带时间 + 天气"做进固件（少刷一屏）。
