> 为什么先做或后做 / 用什么判据验收**。
>
> 这一版（2026-09-28，build 28）把清单里"纯软件、能离线验"的两条先做了：
> **反色**、**旋转 180°**，顺带给了**农历开关**。剩下的排在下面，各自标了风险。

## 0. 先说控制通道：不用改 tsl0922 那套协议

新功能总得有个"开关"。我们**不动**现有协议（网页还是那套 `INIT / WRITE_IMAGE /
REFRESH / SET_TIME`），而是加**私有命令码**，让网页自带的那个「发送命令」框来发：

```js
// work/github/epd-nrf5-user/html/js/main.js
async function sendcmd() {
  const cmdTXT = document.getElementById('cmdTXT').value;   // 十六进制串，比如 "7002"
  const bytes  = hex2bytes(cmdTXT);
  await write(bytes[0], bytes.length > 1 ? bytes.slice(1) : null);
}
```

也就是说：**第一个字节是命令码，后面是 payload**。我们挑没人用的 `0x70~0x7F`
这一段（原厂那套用到 `0x00~0x06 / 0x20 / 0x21 / 0x30 / 0x90~0x99`），
固件对不认识的命令码本来就是"收下不动"，所以加新码不会破坏任何现有行为
（`zk_epd_svc.c` 的 `default:` 分支）。

### 已经实现的：`0x70 SET_OPTIONS`

| 命令 | 作用 |
|---|---|
| `70 00` | 全关（默认状态，跟以前逐字节一样） |
| `70 01` | **反色**（黑白面黑<->白，红面不动） |
| `70 02` | **旋转 180°**（价签挂反了的时候用） |
| `70 04` | 日历页**不画农历**那一行 |
| `70 06` | 位可以叠：旋转 + 不画农历 |

固件侧生效点只有一个：**写屏之前对整帧做变换**（`Src/img/zk_opt.c`）——
网页推来的图和固件自己画的日历/时钟页都经过这里，所以两条路不用各写一遍。
两个变换都是"自逆"的：写完屏再变换一次就把缓冲还原，SWD 信箱那条路读到的
还是上位机写进来的原图。

发完命令会回一条通知 `opt=XX`，网页日志里能直接看到设成了什么；
`bash status.sh` 里也会印一行「画面选项」。

### 已经实现的：激活重试 —— 修掉"固件说刷了、屏没动"（build 47，2026-09-30）

> ⚠ **build 47 的重试策略不够**（2026-09-30 13:30 实测）：它只"重发激活"3 次
> （间隔 200ms），结果 3 次全被屏忽略 —— `写图+刷新 8752 ms / BUSY 7093 次(≈1.4 秒)`，
> 屏上依然没变。真正的规律是**整轮重来**（断电 → 复位 → 初始化 → 写图 → 激活），
> 也就是"一次同步发两条命令时第二条能刷上屏"的那个场景。
> 修法见下面的 **build 48**。

**症状**（用户实测）：Mac 基站推的「晴 34℃」上屏了，之后 ESP32 基站推的「晴 0℃」**怎么推都不上屏**，
屏一直停在旧那页；期间价签调试块却一直说 `画过 6 次`、`屏：刷完一帧了`。

**定位**（`outputs/pyocd/status-20260930-*.log`，看「写图+刷新耗时」和 BUSY 轮询次数）：

| 日志 | 耗时 | BUSY 轮询 | 等价忙时长 | 屏上 |
|---|---|---|---|---|
| 11:04:04 | 7,073 ms | 1,632 | ≈0.3s | ❌ 没变 |
| 11:05:44 | 24,360 ms | 84,907 | ≈17.0s | ✅ 真刷 |
| 12:38:33 | 7,187 ms | 2,397 | ≈0.5s | ❌ 没变 |
| 历史成功（09-27/28/29） | 24~26 s | 83k~90k | 16.7~18.0s | ✅ |

**根因**：每个绘制回合结束都会 `epd_pins_release()`，把 `P1_8(AUX)` 这根**屏供电脚**一起松开；
下一回合是冷启动，面板升压没稳，**第一次 `0x22/0x20` 激活会被它忽略**（BUSY 只忙零点几秒），
要紧跟着的第二次激活才是真空形（17 秒）。所以一次同步里只发一条命令时屏永远不变；
发两条时靠第二条的"热刷"才把画面刷上去。

**修法**（`Src/epd/epd_zk42v.c` 的 `epd_refresh_ex()`）：激活后按 BUSY 轮询次数的差值判真假 ——
忙够 1 秒（≥5000 次轮询）算真刷；没够就缓 200ms 再来一次，**最多 3 次**。

* 镜像：`bin_size = 0x1F71C (128796 字节)`、`check_sum = 0x00C7FB6C`
  （build 46 是 128764 / 0x00C7F706，这次 +32 字节；check_sum 末尾从 6A 变 6C 是因为
  同时把 `ZK_BUILD_ID` 从 46 改成 47，固件自报的版本号才对得上）
* 512k 镜像 SHA-256：`b8aaffa86ea3adb6ac0055f8c21e81b48290363b182281e74cdd5163cff9cf35`
* 离线自测：11 套全过（fwpack / img2epd / dbg_layout / adv_data / lunar / jieqi / weather / bat / opt / tick / gui）
* ~~顺带发现：单调时基疑似跑快 2.95 倍~~ → **已排除**（2026-09-30 13:06 / 13:16 两次 status 复核）：
  13:02 读 `zk_tick_ms()=279457 ms`，跟"价签约 12:57:38 上电 + ESP32 约 13:01:43 推命令"完全吻合
  （误差 <1 秒）；13:06 / 13:16 两次读到的 `距同步时间已经过了 5 秒` 也正好等于
  "时间写完后 5 秒画天气页"的实际间隔。之前那个 2.95 倍是我把**"距上次同步"和"距上次重画"**
  混在一起算，而且中间价签还有过复位 —— 结论撤回。
  另外注意：`zk_tick_ms()` 这个字段**只在"画一页"时写一次**，不是实时值，
  两次 status 读到同一个数（本例 279457）是正常的，别当成时基停了。

### 局刷：阶段性结论（2026-09-30，**暂不做**）

### ✅ 已修：毫秒时基换成 **AON 定时器**（build 59，2026-10-01）

**一句话**：时基不再拿 **CPU 周期**（`DWT->CYCCNT`）算，改用 **AON 定时器**
（`AON->TIMER_VAL`，0xA000C594，低功耗时钟域、与 CPU 主频无关）。
频率在开机时标定（DWT 当尺子），标不出来依次退到 SDK 值、名义值；AON 完全不涨
才退回老实现。**所有证据都写进状态块（104~111 号字），`status.sh` 直接译出来。**

| 项 | 值 |
|---|---|
| 改的文件 | `Src/board/zk_tick.h`（加 `zk_tick_aon_step`）· `Src/main.c`（`zk_timebase_init` + 选择/回退）· `Src/board/zk_dbg.h`（104~111 号字）· `outputs/pyocd/led-window-user.py`（译码 + 实测）· `tools/test_tick.py`（+5 条用例） |
| 镜像 | `bin_size 130224 / check_sum 0x00CAE38F`，SHA-256 `fd4e55cb789d8c9e48f0ae3286076f23b4c6bedc62e1b36a0d32ae35e518a1be`（+592 字节） |
| 自测 | 11 套全过（`test_tick` 从 6 条加到 **11 组**：AON 那条路单独测回绕/除不尽/异常跳变/hz=0） |
| 验收 | `status.sh` 里新加的**时基实测**：`zk_tick_ms` 增量 ÷ 真实秒数 ≈ **1.00**（修之前 3~4.8）；其次是日历在真实 00:00 才换天 |

**实机验收（2026-10-01 12:1x，刷完 build 59 第一次体检）—— 过了** ✅

```
时基实测（拿状态块里的 zk_tick_ms 跟宿主秒表对拍，等了 5.0 秒）：
  价签走了 5.00 秒 / 真实 5.01 秒  ⇒ **比值 0.999**
heart = 19975   flags = 0x2C   build = 59
BUSY 线：见过低=是 见过高=是  轮询=85047  超时=0
```

* 比值 **0.999**（修之前是 3~4.8）⇒ 毫秒时基终于是真实时间了。
* `flags = 0x2C` = `0x04`(DWT_OK) | `0x08`(SWD_ON) | **`0x20`(ZK_FLAG_AON_TB)**
  ⇒ **确实在跑 AON 时基**（不是回退到 CYCCNT 那条路）。这是最关键的一位数：
  光看比值看不出来是谁在计时，但这一位能看出走的是哪条路。
* `BUSY 轮询 = 85047 / 超时 0` ⇒ 那次刷新是真刷（对得上 build 48 的判据）。

还剩一条要等真实时间：**日历在真实 00:00 才换天**（这是这个 bug 的用户可见症状）。
从 2026-10-01 晚上挂到 10-02 零点就能确认。

**为什么是"AON 定时器"**（三条实测，都来自 `outputs/pyocd/status-*.log`）：

1. **它是递减计数器**：474690 → 467688（250 ms 走了 7002）⇒ **~28 kHz**，不是教科书
   式的 32768。所以固件里先探测方向、把"递减"归一成"递增"再累加（`s_aon_down`）。
2. **它跟 CPU 主频无关**：读它的时候 CPU 被调试器停着，它照样在走 —— 这正是我们要的。
3. **CYCCNT 才是那个不靠谱的**：build 58 的观测量记下过一次 `d` = 1e9 个周期，
   按 16 MHz 折成 **62 秒**，而当时真实只过了 **20.8 秒**（正好一次全刷）——
   也就是说刷屏/连 BLE 那段时间里主频远高于 16 MHz，**比值 3.0**。
   空闲时主频又确实是 16 MHz，所以 `status.sh` 的自检一直"看着是对的"。

**实现要点**（踩过的坑都写在代码注释里）：

* 累加**原始 tick**、只在返回时 `tick * 1000 / hz` 除一次 —— 28000 除不尽，
  每次单独折算会有截断误差，越走越慢；
* 单次间隔 ≥ 2³¹（21 小时）当**异常**处理：不计时、只记一笔 `tb_bad`
  （计数器被复位/方向搞反时不会一次跳 21 小时）；
* 标定与 SDK 值**交叉核对**：`sys_lpclk_get()`（ROM，libble_sdk 里也用它）报的数
  与 DWT 标定差 >20% 就信 SDK 的 —— 万一标定那会儿主频不是 16 MHz，标定值会差好几倍，
  这条能把那种情况挡在外面；
* **没动** `epd_delay_us()/epd_delay_ms()`（还是 CYCCNT 折算）：它们只在 SPI 时序和
  BUSY 轮询里用，改了反而要重新校一遍面板时序。**busy 超时是数 200µs 步数的**
  （`epd_wait_busy` 里的 `waited_us`），不受这次改动影响。

**副作用（已知、可接受）**：所有拿 `tick_ms()` 计时的逻辑现在走的是**真实时间**，
所以间隔"变长"了 3~4.8 倍 —— 也就是回到它们**本来该有**的长度：
`zk_bat_poll` 真的每 60 秒读一次电池（以前 ~15 秒）、BLE 广播变体实验的超时是真 3 秒、
日历重画间隔按真时间走。`epd_wait_busy` 的 30 秒超时**不受影响**（它不数 tick）。

### 🚨 待修（**已被 build 59 取代**）：单调时基**快 3 倍**（2026-09-30 发现，用户看到"日历跳到 10 月 1 号"）

**症状**：9-30 晚间（真实 22:58）价签的月历显示 **10 月 1 号**、红圈也挪到 1 号。

**证据**（`outputs/pyocd/status-20260930-225833.log`，build 54）：

```
网页给的时间 = 2026-09-30 16:01:33      ← 推给它的值是对的（16:01 那次推送 16:22 左右到达）
日历/时钟重画：最近一次…距同步时间已经过了 70568 秒   ← 它以为过了 19.6 小时
zk_tick_ms() = 70953419               ← 它以为开机 19.7 小时
→ 而真实只过了约 6.5 小时          ⇒ 比值 ≈ 3.0
```

16:01:33 + 19.6h = 次日 11:37 ⇒ 它把日期画成 10/1，自洽。

**根因（2026-10-01 更新：第一个假设已排除，见下）**：

~~假设 A：`SystemCoreClock` 报 16 MHz 但 CPU 实跑 48 MHz~~ →
**已用 build 55 的观测排除**：`test_step`（现改成打印 `SystemCoreClock`）在**空闲和刷屏+BLE 活动时都读到 16000000**，
而 `status.sh` 自己的时基自检（读两次 CYCCNT 隔 0.26 秒）也一直是 ~16 MHz ⇒ **CYCCNT 确实是 16 MHz、
per_ms=16000 也是对的**，两者都正常，但 `zk_tick_ms()` 依旧快 ~3 倍（两次 status 之间真实几分钟，
它走了 1250 秒）。

**假设 B（现行，最可能）：`zk_tick_step()` 的读改写被**并发调用**破坏了。
`Src/board/zk_tick.h` 里那句注释写着"调用点都在主循环里（不是中断），所以这里的读改写没有并发问题" ——
一旦有中断上下文也调 `zk_tick_ms()` / `zk_tick_ms64()`，就会出现：
A 读到 `cyc=C1` → 被抢占 → B 读到 `C2(>C1)` 并把 `t->cyc` 更新成 `C2` → A 恢复后算 `d = C1 - t->cyc`
= **无符号下溢**（≈4.29e9）→ `whole = d/16000 ≈ 268435` ⇒ **一次性跳 4.5 分钟**。
这与"钟跑快 2~3 倍、且是突发式往前跳"完全吻合，也不影响"CYCCNT 频率测得准"这一点。

**下一步**：① 先加计数（记录 `d` 异常大的次数）验证；② 修法二选一 ——
把读改写放进临界区（关中断），或者**只让主循环喂 tick**、ISR 里只读缓存的 ms 值（更干净）。

（备查）原始假设描述：毫秒是 `CYCCNT / (SystemCoreClock / 1000)` 算的；`SystemCoreClock` 报
**16 MHz**，但 GR5513 在 BLE/刷屏时会把 CPU 拉到 **48 MHz**（48/16 = **3**，正好是实测比值）。
`status.sh` 的"时基自检"只测了**空闲**那一下（16 MHz，看起来对），所以一直没抓到。

**修法（下一版做，build 55 起）**：
1. **首选：改用 AON 定时器**（低功耗时钟，与 CPU 主频无关）。它可读：
   `AON 基址 + 0x94`（就是 `status.sh` 里"读两次隔 250ms"用的那个 `ZK_AON_TIMERV`）。
   做法：累加 32 位自由计数器的**无符号差值**到 64 位，再 `ticks * 1000 / 频率` 换算 —— 不要每次
   单独换算（会有截断误差），累加原始 tick 再换算才不丢精度。
   ⚠ 它的**实际频率必须先标定**：实测 250ms 走了 6617 个 tick ≈ 26.5kHz（不是教科书式的 32.768kHz，
   也可能是 SWD 读取开销导致的时间不准）。标定办法：开机时用 DWT 量一段已知时长内的 tick 数，
   按测得频率换算（这样对晶振偏差也自动补偿）。
2. 次选：每次读数前调 SDK 的 `SystemCoreClockUpdate()`（前提是 SDK 真的会更新它）。
3. 顺带修：`epd_delay_us()` 也是用 `SystemCoreClock` 折算 CYCCNT 的 —— 如果主频被拉到 48MHz，
   那些延时也会**缩短 3 倍**（SPI 时序变快，可能影响面板写入）。

**验证方法**（刷完必做）：`status.sh` 里 `zk_tick_ms()` 的增量 ÷ Mac 秒表的真实秒数 ≈ 1.00
（现在这个比值是 3.0，一眼能看出来）。同时也该看：日历在真实 00:00 才换天。

结论：**机制可行、参数拿不到，先归档**。把今天挖到的线索都留在这儿，将来想捡起来不用重做：

1. **原厂有两条更新路径**（反汇编 `outputs/analysis/epd-seq.txt`）：
   * `func 0x0100FE32`：`0x22=0xC7` + `0x20` —— 就是我们一直在用的**全刷**（BUSY 忙 17 秒）；
   * `func 0x0100FE4E`：`0x18=0x80` / `0x1A=0x55` / `0x22=0xD7` + `0x20`；
   * `func 0x0100FE84`：调上面那条之后，**读一个寄存器取低 3 位当档位 → 查表 `0x0100D8A0`（64/48/16/24/16/32）→ ×10000 tick → 轮询内部计时器等 0.16~0.64 秒**，
     **全程不看 BUSY**。
2. **实测确认 `0xD7 + 短延时` 就是"快刷"**（build 51 的 `76 01`）：
   `写图+刷新 7329 ms`、`BUSY 轮询 49 次（≈0.0 秒）` —— 跟全刷的 24000ms/85000 次形成鲜明对比。
   代价：**整屏用它必发灰**（驱动不足，用户看到的"蒙白布"）；`0x1A` 调到 0xA0/0xF0 甚至**全屏全白**。
3. **社区（qbsg/平平）的"校准局刷参数"不是面板寄存器**：网页那个输入框对应的 JS 是
   `triggerEpdRed_lut(cmd) { cmd = 'E6' + cmd; rxTxSendCommand(...) }` ——
   也就是**私有命令 `E6 <param>`**（`01~0F` 局刷；`10~F0` **关红局刷 + 校准黑局刷，越大越深**），
   参数落到哪个寄存器由**他们的固件**决定。所以照抄没用（我们固件里 `0xE6` 是忽略的）。
   * 但这条印证了物理判断：**三色屏局刷 = 黑白参与、红不参与**（人家直接叫"红 LUT 校准"）。
4. 要做的话，正路是照 **UC8176 datasheet 的 partial 章节**来：局部窗口（`0x90/0x91/0x92`）+
   局刷 LUT（`0x32` 写表，我们固件目前完全不写 LUT）+ `0x22` 的模式位，配"黑白区局刷 + 换天全刷除残影"。
5. 已经加好、**默认关闭**的实验开关（留着以后用）：
   `76 <0/1>`（快刷开关）、`77 [x0 y0 x1 y1]`（局刷窗口）、`78 <param>`（驱动强度字节，试过：不是 `0x1A`）。
6. ⚠ 这些开关是**黏的**，实验完必须 `77`（关）+ `76 00`（关）+ 一次 `sync` 全刷把画面洗干净。

### 已经实现的：写图+刷新**整轮重试**（build 48，2026-09-30）

在 `epd_flush_frame(buf, ctrl)`（`Src/epd/epd_zk42v.c`）里照抄那个"能工作的场景"：

```
for pass in 1..3:
    上电(epd_gpio_init) → 复位(epd_reset) → 参数初始化(epd_init_sequence)
    → 写图(epd_write_image) → 激活(epd_refresh_ex)
    如果这一轮 BUSY 忙够 1 秒（≥5000 次轮询）→ 真刷，返回 pass
    否则 → epd_pins_release()（断电）+ 等 600ms，整轮重来
```

* 调用点：`zk_epd_svc.c` 的 `s_need_refresh` 分支改调 `epd_flush_frame(ZK_IMG_BUF, 0xC7)`，
  不再自己 `zk_panel_ensure_init()` + 写图 + `epd_refresh_ex()`。
* 状态块：`panel_state = 2`（真刷成功）/ `= 3`（三轮都没真刷）；
  `status.sh` 里 3 的中文说明已同步改成"初始化失败 / build 48 起：写图+刷新三轮都没真刷"。
* 代价：冷启动那一次最多多写两遍图（每遍约 6 秒）+ 两次 600ms 等待。

* 镜像：`bin_size = 0x1F73C (128828 字节)`、`check_sum = 0x00C80A2D`
  （build 47 是 128796 / 0x00C7FB6C）
* 512k 镜像 SHA-256：`59ddba0efeef5a861a9ce253b9f226e9745031532b152b531d85ca0e5aa34fb3`
* 离线自测：11 套全过
* **实机验收（2026-09-30 13:37，`status-20260930-133745.log`）**：
  `命令：一共收到 2 条，最后一条 = 0x20`（单命令同步）、
  `屏：刷完一帧了`、`写图+刷新 24389 ms`、`BUSY 85055 次（≈17.0 秒）` —— **真刷 ✅**
  （对照 13:30:18 的 build 47：同样场景只有 8752 ms / 7093 次 = 假刷）。
  也就是说：**"只发一条命令也能把屏刷出来"这件事成立了**，白天天气变化自动更新才有意义。

## 2. 一条硬约束：镜像体积（做新功能前先看这个）

原厂 bootloader 在 `0x0100392A` 处要求 `bin_size ≤ 0x24FC0 = 151488` 字节，超了
直接在 `0x01003720` 死循环（build 26 就是这么"刷完起不来"的，README 顶上记着）。

| build | bin_size | 余量 |
|---|---|---|
| 26 | 156164 | ❌ 超了 4676 |
| 27 | 145732 | 5756 |
| 28 | 147748 | 3740 |
| 29 | 147804 | 3684 |
| 30 | 148004 | 3484 |
| 31（加 ADC 后） | 151212 | ⚠ 只剩 276 |
| **31（换 newlib-nano）** | **123588** | **27900** ✅ |

build 31 那一跳值得记一笔：加 ADC（电池/温度）把浮点库和 libc 的 printf 机制一起
拖了进来，余量只剩 276 字节；Makefile 加一句 `-specs=nano.specs` 之后回到 **27900**。
所以现在做新功能的体积压力小多了（不过**每加一块东西还是先看 `bash build.sh` 报的 bin_size**）。

所以后面每加一个功能：`bash build.sh` 会**硬检查**这个上限（`tools/fwpack.py`），
超了直接拒刷 —— 不会又刷出一块起不来的板子。真要腾地方，按代价从小到大：
`-O2`（现在是 `-Os`）、砍掉用不上的字模/表、把某些页面改成"网页端画好再推图"。
