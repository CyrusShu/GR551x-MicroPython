> 收益最大）」。这份文件就是那张清单的落地版：每一条都写清楚**控制通道 / 怎么做 /
> 为什么先做或后做 / 用什么判据验收**。
>
> 这一版（2026-09-28，build 28）把清单里"纯软件、能离线验"的两条先做了：
> **反色**、**旋转 180°**，顺带给了**农历开关**。剩下的排在下面，各自标了风险。

## 0. 先说控制通道：不用改 tsl0922 那套协议

新功能总得有个"开关"。我们**不动**现有协议（网页还是那套 `INIT / WRITE_IMAGE /
REFRESH / SET_TIME`），而是加**私有命令码**，让网页自带的那个「发送命令」框来发：

```js
// work/github/epd-nrf5-user/html/js/main.js
async function sendcmd() {
  const cmdTXT = document.getElementById('cmdTXT').value;   // 十六进制串，比如 "7002"
  const bytes  = hex2bytes(cmdTXT);
  await write(bytes[0], bytes.length > 1 ? bytes.slice(1) : null);
}
```

也就是说：**第一个字节是命令码，后面是 payload**。我们挑没人用的 `0x70~0x7F`
这一段（原厂那套用到 `0x00~0x06 / 0x20 / 0x21 / 0x30 / 0x90~0x99`），
固件对不认识的命令码本来就是"收下不动"，所以加新码不会破坏任何现有行为
（`zk_epd_svc.c` 的 `default:` 分支）。

### 已经实现的：`0x70 SET_OPTIONS`

| 命令 | 作用 |
|---|---|
| `70 00` | 全关（默认状态，跟以前逐字节一样） |
| `70 01` | **反色**（黑白面黑<->白，红面不动） |
| `70 02` | **旋转 180°**（价签挂反了的时候用） |
| `70 04` | 日历页**不画农历**那一行 |
| `70 06` | 位可以叠：旋转 + 不画农历 |

固件侧生效点只有一个：**写屏之前对整帧做变换**（`Src/img/zk_opt.c`）——
网页推来的图和固件自己画的日历/时钟页都经过这里，所以两条路不用各写一遍。
两个变换都是"自逆"的：写完屏再变换一次就把缓冲还原，SWD 信箱那条路读到的
还是上位机写进来的原图。

发完命令会回一条通知 `opt=XX`，网页日志里能直接看到设成了什么；
`bash status.sh` 里也会印一行「画面选项」。

### 已经实现的：激活重试 —— 修掉"固件说刷了、屏没动"（build 47，2026-09-30）

> ⚠ **build 47 的重试策略不够**（2026-09-30 13:30 实测）：它只"重发激活"3 次
> （间隔 200ms），结果 3 次全被屏忽略 —— `写图+刷新 8752 ms / BUSY 7093 次(≈1.4 秒)`，
> 屏上依然没变。真正的规律是**整轮重来**（断电 → 复位 → 初始化 → 写图 → 激活），
> 也就是"一次同步发两条命令时第二条能刷上屏"的那个场景。
> 修法见下面的 **build 48**。

**症状**（用户实测）：Mac 基站推的「晴 34℃」上屏了，之后 ESP32 基站推的「晴 0℃」**怎么推都不上屏**，
屏一直停在旧那页；期间价签调试块却一直说 `画过 6 次`、`屏：刷完一帧了`。

**定位**（`outputs/pyocd/status-20260930-*.log`，看「写图+刷新耗时」和 BUSY 轮询次数）：

| 日志 | 耗时 | BUSY 轮询 | 等价忙时长 | 屏上 |
|---|---|---|---|---|
| 11:04:04 | 7,073 ms | 1,632 | ≈0.3s | ❌ 没变 |
| 11:05:44 | 24,360 ms | 84,907 | ≈17.0s | ✅ 真刷 |
| 12:38:33 | 7,187 ms | 2,397 | ≈0.5s | ❌ 没变 |
| 历史成功（09-27/28/29） | 24~26 s | 83k~90k | 16.7~18.0s | ✅ |

**根因**：每个绘制回合结束都会 `epd_pins_release()`，把 `P1_8(AUX)` 这根**屏供电脚**一起松开；
下一回合是冷启动，面板升压没稳，**第一次 `0x22/0x20` 激活会被它忽略**（BUSY 只忙零点几秒），
要紧跟着的第二次激活才是真空形（17 秒）。所以一次同步里只发一条命令时屏永远不变；
发两条时靠第二条的"热刷"才把画面刷上去。

**修法**（`Src/epd/epd_zk42v.c` 的 `epd_refresh_ex()`）：激活后按 BUSY 轮询次数的差值判真假 ——
忙够 1 秒（≥5000 次轮询）算真刷；没够就缓 200ms 再来一次，**最多 3 次**。

* 镜像：`bin_size = 0x1F71C (128796 字节)`、`check_sum = 0x00C7FB6C`
  （build 46 是 128764 / 0x00C7F706，这次 +32 字节；check_sum 末尾从 6A 变 6C 是因为
  同时把 `ZK_BUILD_ID` 从 46 改成 47，固件自报的版本号才对得上）
* 512k 镜像 SHA-256：`b8aaffa86ea3adb6ac0055f8c21e81b48290363b182281e74cdd5163cff9cf35`
* 离线自测：11 套全过（fwpack / img2epd / dbg_layout / adv_data / lunar / jieqi / weather / bat / opt / tick / gui）
* ~~顺带发现：单调时基疑似跑快 2.95 倍~~ → **已排除**（2026-09-30 13:06 / 13:16 两次 status 复核）：
  13:02 读 `zk_tick_ms()=279457 ms`，跟"价签约 12:57:38 上电 + ESP32 约 13:01:43 推命令"完全吻合
  （误差 <1 秒）；13:06 / 13:16 两次读到的 `距同步时间已经过了 5 秒` 也正好等于
  "时间写完后 5 秒画天气页"的实际间隔。之前那个 2.95 倍是我把**"距上次同步"和"距上次重画"**
  混在一起算，而且中间价签还有过复位 —— 结论撤回。
  另外注意：`zk_tick_ms()` 这个字段**只在"画一页"时写一次**，不是实时值，
  两次 status 读到同一个数（本例 279457）是正常的，别当成时基停了。

用户刷了 build 67 + 基站 build-8，屏上**没有框**，`status.sh` 显示
`纪念日 0x7A：收到 0 次`。ESP32 日志是这样的：

```
[20s] → 城市名 深圳（温度后面那几个字）        ← 7 字节，一次写完 ✓
[60s] → 纪念日 10-05「付婧文生日快乐！」…      ← 卡了 40 秒才返回，而且没送达 ✗
```

**根因：BLE 的 ATT 一次只能发 `MTU-3` 字节，而 ESP32 基站的 MTU 还是默认的 23
（= 20 字节）。** 那条纪念日是 `3 + 24 = 27` 字节 → Bluedroid 自动改用"长写
（prepare write / execute write）"，而价签的 GATT 不支持这条路径 → 写入卡到超时。
城市名 7 字节、时间+天气 10 字节都在 20 以内，所以之前一直没暴露。

**修法**（两端配合，跟 MTU 多大彻底无关）：

* 固件加 **`0x7B` MEMO_MORE**（续传一段文案）：`0x7A` 起头（带月日、清空缓冲），
  后面每段用 `0x7B` 追加，固件只管把字节攒进 `s_memo`。
* ESP32 基站按 **≤15 字节文案**切（`3+15=18`、`1+15=16`，都在 20 以内），
  并且**只在 UTF-8 字符边界上切**。
* 顺手也做了 **MTU 协商**（`client->setMTU(247)`，价签支持到 244）：谈成了以后
  一次能发 244 字节，长文案不用分片；谈不成也不影响（上面那套分片兜着）。

> ⚠ 字符边界那行判断我第一版写反了：检查"本段最后一个字节是不是续字节"，结果把
> 汉字切成 `[13, 9, 1, 1]` 这种碎片（拼回来虽然还对，但很难看、也可能被别的实现挑刺）。
> 正确做法是看**下一段的第一个字节**：是 `10xxxxxx`（续字节）就说明正好切在字中间，
> 往前退。这个 bug 是拿 Python 把分片逻辑跑了一遍才发现的（`[15, 9]` ✓）——
> **以后凡是"按字节切多字节编码"的活，都先跑一遍模拟**。

**为什么是"AON 定时器"**（三条实测，都来自 `outputs/pyocd/status-*.log`）：

1. **它是递减计数器**：474690 → 467688（250 ms 走了 7002）⇒ **~28 kHz**，不是教科书
   式的 32768。所以固件里先探测方向、把"递减"归一成"递增"再累加（`s_aon_down`）。
2. **它跟 CPU 主频无关**：读它的时候 CPU 被调试器停着，它照样在走 —— 这正是我们要的。
3. **CYCCNT 才是那个不靠谱的**：build 58 的观测量记下过一次 `d` = 1e9 个周期，
   按 16 MHz 折成 **62 秒**，而当时真实只过了 **20.8 秒**（正好一次全刷）——
   也就是说刷屏/连 BLE 那段时间里主频远高于 16 MHz，**比值 3.0**。
   空闲时主频又确实是 16 MHz，所以 `status.sh` 的自检一直"看着是对的"。

**实现要点**（踩过的坑都写在代码注释里）：

* 累加**原始 tick**、只在返回时 `tick * 1000 / hz` 除一次 —— 28000 除不尽，
  每次单独折算会有截断误差，越走越慢；
* 单次间隔 ≥ 2³¹（21 小时）当**异常**处理：不计时、只记一笔 `tb_bad`
  （计数器被复位/方向搞反时不会一次跳 21 小时）；
* 标定与 SDK 值**交叉核对**：`sys_lpclk_get()`（ROM，libble_sdk 里也用它）报的数
  与 DWT 标定差 >20% 就信 SDK 的 —— 万一标定那会儿主频不是 16 MHz，标定值会差好几倍，
  这条能把那种情况挡在外面；
* **没动** `epd_delay_us()/epd_delay_ms()`（还是 CYCCNT 折算）：它们只在 SPI 时序和
  BUSY 轮询里用，改了反而要重新校一遍面板时序。**busy 超时是数 200µs 步数的**
  （`epd_wait_busy` 里的 `waited_us`），不受这次改动影响。

**副作用（已知、可接受）**：所有拿 `tick_ms()` 计时的逻辑现在走的是**真实时间**，
所以间隔"变长"了 3~4.8 倍 —— 也就是回到它们**本来该有**的长度：
`zk_bat_poll` 真的每 60 秒读一次电池（以前 ~15 秒）、BLE 广播变体实验的超时是真 3 秒、
日历重画间隔按真时间走。`epd_wait_busy` 的 30 秒超时**不受影响**（它不数 tick）。

（备查）原始假设描述：毫秒是 `CYCCNT / (SystemCoreClock / 1000)` 算的；`SystemCoreClock` 报
**16 MHz**，但 GR5513 在 BLE/刷屏时会把 CPU 拉到 **48 MHz**（48/16 = **3**，正好是实测比值）。
`status.sh` 的"时基自检"只测了**空闲**那一下（16 MHz，看起来对），所以一直没抓到。

**修法（下一版做，build 55 起）**：
1. **首选：改用 AON 定时器**（低功耗时钟，与 CPU 主频无关）。它可读：
   `AON 基址 + 0x94`（就是 `status.sh` 里"读两次隔 250ms"用的那个 `ZK_AON_TIMERV`）。
   做法：累加 32 位自由计数器的**无符号差值**到 64 位，再 `ticks * 1000 / 频率` 换算 —— 不要每次
   单独换算（会有截断误差），累加原始 tick 再换算才不丢精度。
   ⚠ 它的**实际频率必须先标定**：实测 250ms 走了 6617 个 tick ≈ 26.5kHz（不是教科书式的 32.768kHz，
   也可能是 SWD 读取开销导致的时间不准）。标定办法：开机时用 DWT 量一段已知时长内的 tick 数，
   按测得频率换算（这样对晶振偏差也自动补偿）。
2. 次选：每次读数前调 SDK 的 `SystemCoreClockUpdate()`（前提是 SDK 真的会更新它）。
3. 顺带修：`epd_delay_us()` 也是用 `SystemCoreClock` 折算 CYCCNT 的 —— 如果主频被拉到 48MHz，
   那些延时也会**缩短 3 倍**（SPI 时序变快，可能影响面板写入）。

**验证方法**（刷完必做）：`status.sh` 里 `zk_tick_ms()` 的增量 ÷ Mac 秒表的真实秒数 ≈ 1.00
（现在这个比值是 3.0，一眼能看出来）。同时也该看：日历在真实 00:00 才换天。

结论：**机制可行、参数拿不到，先归档**。把今天挖到的线索都留在这儿，将来想捡起来不用重做：

1. **原厂有两条更新路径**（反汇编 `outputs/analysis/epd-seq.txt`）：
   * `func 0x0100FE32`：`0x22=0xC7` + `0x20` —— 就是我们一直在用的**全刷**（BUSY 忙 17 秒）；
   * `func 0x0100FE4E`：`0x18=0x80` / `0x1A=0x55` / `0x22=0xD7` + `0x20`；
   * `func 0x0100FE84`：调上面那条之后，**读一个寄存器取低 3 位当档位 → 查表 `0x0100D8A0`（64/48/16/24/16/32）→ ×10000 tick → 轮询内部计时器等 0.16~0.64 秒**，
     **全程不看 BUSY**。
2. **实测确认 `0xD7 + 短延时` 就是"快刷"**（build 51 的 `76 01`）：
   `写图+刷新 7329 ms`、`BUSY 轮询 49 次（≈0.0 秒）` —— 跟全刷的 24000ms/85000 次形成鲜明对比。
   代价：**整屏用它必发灰**（驱动不足，用户看到的"蒙白布"）；`0x1A` 调到 0xA0/0xF0 甚至**全屏全白**。
3. **社区（qbsg/平平）的"校准局刷参数"不是面板寄存器**：网页那个输入框对应的 JS 是
   `triggerEpdRed_lut(cmd) { cmd = 'E6' + cmd; rxTxSendCommand(...) }` ——
   也就是**私有命令 `E6 <param>`**（`01~0F` 局刷；`10~F0` **关红局刷 + 校准黑局刷，越大越深**），
   参数落到哪个寄存器由**他们的固件**决定。所以照抄没用（我们固件里 `0xE6` 是忽略的）。
   * 但这条印证了物理判断：**三色屏局刷 = 黑白参与、红不参与**（人家直接叫"红 LUT 校准"）。
4. 要做的话，正路是照 **UC8176 datasheet 的 partial 章节**来：局部窗口（`0x90/0x91/0x92`）+

5. 已经加好、**默认关闭**的实验开关（留着以后用）：
   `76 <0/1>`（快刷开关）、`77 [x0 y0 x1 y1]`（局刷窗口）、`78 <param>`（驱动强度字节，试过：不是 `0x1A`）。
6. ⚠ 这些开关是**黏的**，实验完必须 `77`（关）+ `76 00`（关）+ 一次 `sync` 全刷把画面洗干净。

### 已经实现的：写图+刷新**整轮重试**（build 48，2026-09-30）

## 2. 一条硬约束：镜像体积（做新功能前先看这个）

原厂 bootloader 在 `0x0100392A` 处要求 `bin_size ≤ 0x24FC0 = 151488` 字节，超了
直接在 `0x01003720` 死循环（build 26 就是这么"刷完起不来"的，README 顶上记着）。

| build | bin_size | 余量 |
|---|---|---|
| 26 | 156164 | ❌ 超了 4676 |
| 27 | 145732 | 5756 |
| 28 | 147748 | 3740 |
| 29 | 147804 | 3684 |
| 30 | 148004 | 3484 |
| 31（加 ADC 后） | 151212 | ⚠ 只剩 276 |
| **31（换 newlib-nano）** | **123588** | **27900** ✅ |

build 31 那一跳值得记一笔：加 ADC（电池/温度）把浮点库和 libc 的 printf 机制一起
拖了进来，余量只剩 276 字节；Makefile 加一句 `-specs=nano.specs` 之后回到 **27900**。
所以现在做新功能的体积压力小多了（不过**每加一块东西还是先看 `bash build.sh` 报的 bin_size**）。

所以后面每加一个功能：`bash build.sh` 会**硬检查**这个上限（`tools/fwpack.py`），
超了直接拒刷 —— 不会又刷出一块起不来的板子。真要腾地方，按代价从小到大：
`-O2`（现在是 `-Os`）、砍掉用不上的字模/表、把某些页面改成"网页端画好再推图"。

## 4. build 71：天气预警为什么长这样（2026-10-02）

**起因**：用户发现"手机上是局地雷暴雨、还挂着暴雨警报，价签却写小雨"。查下来是两件事：

1. **和风的实况文字本来就是"小雨"** —— 那是我给的坐标（22.7809, 113.8861 = 光明区）
   的格点/观测值；手机顶部那条"局地雷暴雨"其实是**预警 + 雷达**的说法，不是同一个产品。
2. 手机那条**暴雨警报**，和风是有单独接口的（用户的项目也开了）。所以"预警"这一路
   必须单独取、单独画。

**顺手踩到的坑**：老接口 `/v7/warning/now` 已经被和风**下架**，返回
`403 Deprecated（"Please use the latest version"）`。新的是

```
GET /weatheralert/v1/current/{latitude}/{longitude}     ← ⚠ 纬度在前
{ "metadata": {...}, "alerts": [ {eventType, severity, color, headline, expireTime, …} ] }
```

（和风自己都不统一：`/v7/weather/now` 的参数是"经度,纬度"，这个是"纬度/经度"。）

**数据流**（和 build-61 的城市名一样，固件不联网）：

```
和风 /weatheralert ──(NAS 上的 wx-relay.py，HTTPS+JWT)──> 基站读 JSON
        ──(BLE 0x7C)──> 固件表头那格改画预警名
```

**为什么顶掉"天气文字"而不是另找地方画**：表头 400px 已经排满
（`2026年10月 | 丙午 马年 八月 | 图标 天气文字 温度 城市 | 电池`），
加字只能挤掉别人。而"官方正在生效的预警"比"当前天气叫什么"更该占这个位置
—— 天气大类看图标就知道。

**颜色**：这块三色屏只有黑/白/红。级别 ≥3（黄/橙/红）画红，1~2（白/蓝）画黑
—— 黄在国内的气象预警体系里已经是"要行动了"的那一档。

**字模**：只能画 `gen_font.py` 里 `ALERT_CHARS` 那批字（60 个，暴雨雷电大风台风高温…）。
只进 `SMALL_CHARS`（11px）**不进 `CJK_ORDER`**：表头那格用的本来就是小一号的
天气文字，16px 那张表再存一份白占 2KB flash。认不出的字会**截断到那儿**，
所以"雷雨大风"实际画的是"雷雨大"（表头那格就 3 个字的宽度）。

**每天/每次推送的行为**：预警和天气**是两条独立的路** —— 预警取不到（没 key、
接口抽风、中继关机）不影响天气照常推。预警**值没变就不发**（省一次 17 秒全刷）；
预警结束会专门发一条 `7C 00` 把屏上那条清掉，免得挂一条过期的。
基站侧还有个"12 小时没更新就当作过期"的兜底（`alertLevelNow()`）。

## 5. build 72：合并刷新窗口（"开机别刷那么多次"）

**怎么发现的**：用户说开机刷太频繁，于是先把日志里那几条命令数了一遍 —— 5 条命令、
5 次全刷、约 80 秒。根因在 `zk_epd_svc_poll()`：

```c
s_need_gui = 1;                                   /* 每条命令 */
...
if (s_need_gui) { s_need_gui = 0; 画一页; 写图 + 刷 16 秒; }   /* poll 每 5ms 一圈 */
```

标志**在开始重画的那一刻**就被清掉，而刷新是阻塞的十几秒 —— 于是后面来的命令
一律排成"下一次重画"。一次连接里连发 3 条就是 3 次。

**改法**：`gui_request_redraw()` 把预约时间推到 `now + 2 秒`，poll 到点才画；
2 秒内有新命令就继续往后推。比较写成 `(int32_t)(zk_tick_ms() - s_gui_due_ms) >= 0`
—— 毫秒计数器是 32 位会绕圈，直接比大小会出错（build 30 那个"每 4.5 分钟自己刷一次"
就是绕圈咬的）。

**为什么是 2 秒**：同一条连接内部的命令间隔是几十毫秒（纪念日的两段之间有 20ms 的
`delay`）到 1 秒（时间天气 → 预警）；而下一轮连接是几十秒以后。2 秒刚好把"一轮"框住。

**没有漏刷新**：日历页每天换天、时钟页每分钟本来就有自己的重画条件，它们走的是
另一个分支（`else if`），不受这个窗口影响。

> 🔧 build 73 修了这条的一个漏洞：有挂起请求时，那两个分支**不许插队** ——
> 价签刚上电 `s_drawn_day = 0`，第一条命令一到"换天"就成立、当场先画一版
> （那时城市名/预警还没到），用户看到"刷两次，第一次阴、第二次暴雨"。

## 8. 省电第一版（build 75，2026-10-03）—— 用户："价签是 2450 电池，需要省电"

**先搞清原厂怎么做的**（从原厂串口日志 + 反汇编里挖出来的）：

```
batt_volt=3308
no AP, sleep 30000s          ← 找不到基站就睡 30000 秒（8 小时 20 分）
```

反汇编 `0x10137B2` 那段印证了：全局 `0x8043E0` = "本次睡多久"、`0x8043E4` = "正常间隔"；
找不到 AP 就把前者顶到 30000 并置标志，找到 AP 就恢复成配置里的值。
`0x1011478` 是开机读配置（17 + 16 字节）再把 0x8043E4 复制到 0x8043E0 ——
**唤醒间隔是基站下发/配置的**，不是写死的。而且它会把当前间隔**回报给基站**
（`0x101B738` 组一个 5 字节响应，命令字节 `0x96`=150）。

**但原厂那套不能直接抄**（用户一针见血）：那是**价签**逻辑 —— 屏上内容不变就不用醒；
我们是**日历**，**半夜必须醒一次把"今天"那格搬走**，否则第二天屏上还是昨天。

**这一版做了什么**（`Src/board/zk_pwr.h` 里三个旋钮，出问题一键回退 `ZK_PWR_SAVE 0`）：

| 改了什么 | 之前 | 现在 | 为什么 |
|---|---|---|---|
| 主循环 | `epd_delay_ms(5)` **忙等**（CPU 一直跑，200Hz） | SDK `app_timer` 节拍（500ms）+ `pwr_mgmt_mode_set(PMR_MGMT_SLEEP_MODE)` | app_timer 建在 **AON 睡眠定时器**上，电源管理知道下一个到期点，能把 CPU **精确睡到那一刻** |
| 广播间隔 | 100ms（`duration=0` 永不超时） | **1000ms** | 射频平均电流大致降一个数量级；基站扫 6 秒照样抓得到，连接最多慢 1 秒 |

**为什么不用 UDS（超深睡）**：SDK 的 `PMR_MGMT_SLEEP_MODE` 就是 "Deep sleep state"，
**RAM 保持** —— `s_ts`、上一屏、连接状态都还在，醒来几毫秒；而 UDS 醒来等于
**整个系统复位**（原厂就是那套），必须先把"时间持久化"（写 flash）做了才能用，
否则每次醒来都是空日历。

**一个关键前提仍然成立**：毫秒时基跑在 AON 域 —— **睡着的时候它照样在涨**，
醒来算一下"现在几点"就知道有没有换天。所以"日期准"这件事不需要 CPU 一直醒着。

**还没做（下一步）**：
1. **广播限时**（只在唤醒窗口里广播 8~10 秒）—— 这个收益最大，但要配合**基站侧**：
   现在基站把"重新看到价签"当成"价签刚上电"，每次都会整包重推 + 刷一屏；
   窗口化之后就会变成"每醒一次刷一屏"，反而更费电。修法：**用价签连接时上报的
   `t=<epoch>` 判断**（t=0 = 真的刚重启，t≈当前 = 只是睡醒），不用改协议。
2. **唤醒间隔由基站下发**（学原厂）：白天 5 分钟、夜里 30 分钟、有预警时加密。
3. **时间持久化**（写 flash）—— 换电池后 RAM 全丢，没这个醒来就是空日历。

**验收**（这一版要实机确认的）：
· 串口/状态块：`flags` 里 bit6（0x40）应当亮起 → `status.sh` 现在会译成
  "省电版在跑"；
· 价签该刷屏还能刷（让基站推一次看屏）；
· **电流**（关键，我没有这个数据）：CR2450 约 600mAh，想看能撑多久就得测平均电流。

### ⛔ 2026-10-04 实机翻车：**睡眠那一路在这颗芯片上走不通**（build 76 已回退）

刷上 build 75 后：基站**能扫到价签**（rssi -56），但**连 20 秒超时**，34 秒后价签
"从空中消失"。status.sh 把原因钉死了：

| 读数 | 说明 |
|---|---|
| `heart = 1` | 主循环**只跑了 1 圈**就再没动过 |
| PC 停在 `libble_sdk.a(sdk_pwr_mgmt_patch.o)` 的 RAM 代码 | CPU **卡在 SDK 的电源管理代码里打转** |
| AON 计数器连读两次都是 `0xFFFFFFFF`、时基比值 **0.000** | 低功耗时钟/睡眠定时器**没在跑** |
| `IRQ25 BLESLP = 没使能` | BLE 的**睡眠协调中断**没起来 |
| `BLE state=1（在广播）` + `连接：还没有客户端连上来过` | 广播是 BLE 核自己在发（所以扫得到），但**协议栈醒不过来处理连接** → 连不上 |
| `boot_count = 2` | 不是复位循环，是"卡在里面" |

**根因**：我们的毫秒时基（build 59）把 **AON 睡眠定时器**当自由计数器用；而 SDK 的
睡眠入口 + `app_timer` 要**拿同一个定时器**设唤醒倒计时 —— 两边抢同一个硬件。
再加上这颗价签**没有 32.768k 晶振**（`CFG_LPCLK_INTERNAL_EN=1` 走内部 RC，
见 `config/custom_config.h` 里那条"死在 platform_disable_sleep_timer()"的记录），
睡眠路径本来就敏感。所以：**要睡眠，得先把"谁拥有那个 AON 定时器"理清楚** ——
不是加两行 `pwr_mgmt_mode_set()` 就能省电的。

**build 76 的回退**：`ZK_PWR_SAVE=0`（睡眠代码整段编掉，回到忙等），
**但保留广播间隔 100ms → 1000ms**（这条不依赖睡眠，而且 build 75 那次实验里已经
顺带验证过：睡眠卡死的情况下基站照样在 1 秒间隔下扫到了价签）。

**下一步（省电）**：
1. 先量**当前（build 76）的平均电流** —— 有了基准才知道"广播放宽"这一刀省了多少、
   后面值不值得啃睡眠；
2. 要啃睡眠，先解决定**定时器归属**：要么给时基换一个不属于睡眠定时器的计数器
   （查 GR551x 手册：RTC / 另一个 AON 计数器），要么**不用 SDK 的 app_timer**、
   自己写睡眠入口（这条风险大，得先看懂 `sdk_pwr_mgmt_patch.o`）。

## 9. build 77：价签「连上就主动报一次 t=」（2026-10-04 上午）

**现象**（用户："刷了 2 次是为什么"）：基站日志里出现一个**自我维持的循环** ——

```
推送 → 价签刷屏 16 秒（这期间基站扫不到它）→ 基站判"它刚从空中消失了"
→ 再扫到 → 判"它刚上电" → 整包重推 → 又刷 16 秒 → …（27~36 秒白刷一次）
```

**为什么会绕回来**：`zk_epd_svc.c` 里那条 `t=` **不是"连上就发"**，而是
`case 0x20`（SET_TIME）处理完之后的**回包**。基站想在"写之前"先问一句
「你的钟还在走吗」，可它不发命令价签就不回话 —— 于是基站只能等到超时，
判定"说不清"，保守地按"重启"处理，整包重推。**恶性循环的最后一环就在这里。**

**改法**：让价签**主动**开口（协议版本 `0x1a → 0x1b`，基站靠它区分新旧固件）：

* `zk_epd_svc_on_write`：CCCD 一被写上（订阅通知）就预约 `s_need_time_report = 1`；
* `zk_epd_svc_poll`：紧跟着「配置」那条通知之后发 `t=<s_ts>`
  （**必须排在配置之后** —— 网页按「第 0 条通知」解析引脚/驱动型号）；
* `s_ts == 0`（刚上电 / 换过电池）**也发**，发 `t=0`。这样"不回话"和
  "回话说我没时间"才分得开：
  * 回 `t=0` → 真重启 → 基站整包重推；
  * 回真实时间 → 没重启 → 基站一条命令都不写；
  * **什么都不回** → 它正堵在 16 秒全刷里（主循环被占着）→ 基站**这轮先别动它**。

基站侧（`zk_ble_base.py`）：等 6 秒（覆盖"它正堵在全刷里"的极端情况）；
没等到而固件 `>= 0x1b` 就**什么都不写**（写下去就是又刷一屏，正是那个死循环）；
老固件 `<= 0x1a` 保持原样（它确实不会主动回话）。

**影响面检查**：网页 `main.js` 只把 `idx == 0` 当配置、其余走文本分支（`t=` 那条
本来就有处理），所以多这一条通知无副作用；ESP32 基站的 notify 回调只打印，也不受影响。

### ② `异常（计数器倒退/被复位）= 11 / 37 次` —— 是**睡眠定时器被周期性重新装载**（已查清）

同一份日志里：

```
异常（计数器倒退/被复位）= 11 次   长阻塞补记（>1 秒）= 0 次
```

固件 `zk_tick_aon_step()` 里 `bad++` 的条件是"两次读数之差 ≥ 2^31"，注释写的是
"计数器被复位，或者方向搞反了"。在 SDK 头文件里找到了更可能的第三种：

**`AON->TIMER_VAL`（0xA000C594）是个复用寄存器** —— 它当前反映哪个计数器，
由 `AON_PAD_CTL1` 的第 30~31 位 `TIMER_READ_SEL` 选：

| TIMER_READ_SEL | 读的是 |
|---|---|
| 0 | `CAL_TIMER`（日历计数器） |
| 1 | `AON_WDT`（看门狗） |
| 2 | `SLP_TIMER`（睡眠定时器） |
| 3 | `CAL_ALARM`（日历闹钟） |

SDK 自己的每个访问点都是**先选再读**（`gr55xx_ll_calendar.h` 的
`ll_calendar_get_counter()`、`gr55xx_ll_aon_wdt.h` 的 `ll_aon_wdt_get_counter()`，
而且用 `GLOBAL_EXCEPTION_DISABLE/ENABLE` 把这一段包起来）；
**我们的固件是直接 `AON->TIMER_VAL` 一路读下来的，从没设过这个选择子。**
所以只要别的代码（SDK 睡眠路径 / 看门狗 / 日历 / ADC）把选择子挪走一次，
我们下一条读到的就是**另一个计数器**，差值当然没意义 → `bad++`。

危害不只是那个计数：差值万一落在 2^31 以内（只是"看起来像正常增量"），
时钟会**一次性往前跳**（最多 ~22 小时，足够让日历跨一天）—— 跟 build 29/56
那两次的症状一模一样，只是触发概率低。

**实测（2026-10-04 18:10 的 status，build 77）**：`AON_PAD_CTL1 = 0x800000FF`、
`TIMER_READ_SEL = 2 → SLP_TIMER` —— **选择子是对的**，我们读的确实是睡眠定时器。
所以 `bad` 不是"读错了计数器"。

那就把"到底发生了什么"算清楚。用你积累的全部 status 日志做对账（同一次运行里
相邻两次的增量）：

* `累计 tick` 的增量 **就是**"原始计数器净降了多少" —— 有一组 19 秒的窗口里
  两者**一模一样**（511726 = 511726，`bad` 没涨）。也就是说固件就是把递减量加起来；
* 一旦 `bad` 涨了，就会多出来一块"向上跳"的量：`Δ累计tick − 计数器净降量`。
  把这个量除以 `Δbad`：

| 窗口 | Δbad | 每次"向上跳" | 换算成秒 |
|---|---|---|---|
| 10-01 12:50→12:51 | 5 | 653413 tick | **24.00 s** |
| 10-01 12:52→12:54 | 5 | 653432 tick | **24.00 s** |
| 10-01 12:51→12:52 | 1 | 816716 tick | **29.99 s** |
| 10-04 18:00→18:10 | 26 | 596809 tick | 21.92 s（多个周期混在一起） |

两个独立窗口给出 653413 / 653432，**差 0.003%** —— 这不是随机噪声，
是**一个固定的装载值**：653420 tick ÷ 27230 tick/秒 = **24.00 秒**（另一组 30.00 秒）。

**结论**：有人在**周期性地把 AON 睡眠定时器重新装载**（24 秒 / 30 秒 一轮，
典型值就是"下个周期定时器还要多久"）。定时器一被装载，计数器就从当前的小值
跳到装载值 —— 在固件眼里就是"往上跳"，`bad++`。

代价只有一个**读取间隔**（主循环 ~5 ms 一轮），不是把整段时间丢了：

| 对账 | 结果 |
|---|---|
| 18:00:49 → 18:10:42（真实 593 秒） | 累计 tick 走了 **593.03 秒** ✅ |
| 同一份日志的「时基实测」 | 12.00 s / 12.00 s，**比值 0.999** ✅ |

所以它是**正常的**，只是名字吓人（固件里那个字段叫 `tb_bad`、脚本里印成"异常"）。
这一轮只改了**诊断脚本**：把它印成"计数器「向上跳」"，并把 `累计tick ÷ 次数`
和 `AON TIMER_VALUE`（0x90，装载暂存寄存器）一起印出来 —— 直接看装载值对不对得上。

**留一个心眼**：这个判据只在"跳不超过 2^31"时成立。现在的装载值 ~653k
（= 24 秒）离 2^31（≈ 21.9 小时）十万八千里，所以安全；但要是哪天有人
用一个大值去装载（比如真上了睡眠、一睡几小时），固件会把它**当成"时间往前跳"**
而照单全收 —— 那才是"日历突然跨一天"的隐患。要彻底干净，得让固件
**自己拥有一个计数器**（这正是 build 75 卡住的那个问题），或者至少把
"向上跳"和"读取间隔补偿"分开计数。

## 11. 啃睡眠（第二版，2026-10-04 晚）—— build 75 为什么挂死：**暖启动没接**

用户："先啃睡眠吧，之前你趟过坑。" 这次把 build 75 的现场翻了个底朝天，找到了**确定性的根因**。

### ① 直接根因：深睡唤醒是"暖启动"，而我们的 `main_init()` 无视了它

GR551x 的启动链是：

```
Reset_Handler:  bl SystemInit  →  bl main_init        ← 注意：不是 main()
```

SDK 自带的 `main_init()`（`platform/soc/common/gr_platform.c`，`__WEAK`）长这样：

```c
void main_init(void) {
    boot_mode_t boot_flag = pwr_mgmt_get_wakeup_flag();
    if (COLD_BOOT == boot_flag) { __main(); }          /* 冷启动：正常跑 */
    else { warm_boot_process(); for (;;) { } }         /* 暖启动：恢复现场，永不返回 */
}
```

**深睡唤醒 = 从复位向量重新开始**（RAM 保持、上下文靠 `pwr_mgmt_warm_boot()` 恢复）。
所以那条 else 分支是必需的。而**我们那份 `main_init()`（build 30 左右接管的）是
故意不看这个 flag 的**（见 `Src/main.c` 里那段注释：怕从 bootloader 跳进来时判错、
导致 `main()` 永远不被调用），永远走 `__main()`。

后果：一开睡眠 → 睡下去 → 醒来（暖启动）→ 我们把暖启动当冷启动 →
**重跑 C 运行时（`__main()` 会清 .bss、拷 .data）+ 重新初始化 BLE 协议栈** →
状态全乱 → 卡死。

**证据**（build 75 那两份 status）：

| 现场 | 读数 | 说明 |
|---|---|---|
| `boot_count` | **2** | `main_init` 进了**两次**，而那次没有别的复位源 —— 一次冷启动 + 一次暖启动 |
| PC 落点 | `0x30009C38` = `pwr_mgmt_schedule+0x4c`（正要 `bl save_context_and_enter_sleep`）| 第一次循环就进了睡眠 |
| 另一份 PC | `0x3000999A` = `pwr_mgmt_shutdown_patch` 入口，栈上有 `pwr_enter_sleep_check`、`sys_device_sram_get` | 醒来后在 RAM patch 里打转 |
| `heart` | 1 | 主循环只跑了一圈 |
| `AON 计数器` | 连读两次 `0xFFFFFFFF` | 睡眠定时器被装成 `APP_TIMER_OVERFLOW_VALUE`（=0xFFFFFFFF），所以我们的时基读到死值 |

### ② 第二个坑（还没踩到，但一定会踩）：**SDK 自己占着 AON 睡眠定时器**

`platform/soc/src/gr_soc.c` 的 `soc_init()` 里有：

```c
system_pmu_calibration_init(30000);        /* 自动 PMU 校准，默认周期 30 秒 */
```

而 `components/libraries/pmu_calibration/pmu_calibration.c` 里，这个"定时器"是拿
**app_timer** 实现的，并且（内部 RC 那档 `CFG_LPCLK_INTERNAL_EN`）会按
**500ms → 5s → 30s** 自适应地跑 LFRC32k 校准。`app_timer` 底层做的事是：

```c
hal_sleep_timer_config_and_start(PWR_SLP_TIMER_MODE_SINGLE, lpcycles);   /* 单一模式，反复重装 */
```

**也就是说：AON 睡眠定时器是 SDK 的，而且它一直在重装它。** 这正好解释了我们前两轮
测到的"向上跳"：24.00 秒 / 30.00 秒的固定装载值 —— 那是 app_timer 下一次到期的倒计时。

我们的毫秒时基（build 59）恰恰是**读这同一个定时器**的当前值。

* 今天（不睡）只是丢几个毫秒，无所谓；
* **一旦真睡下去**，SDK 会把它当"倒计时唤醒源"用（一睡可能就是几十秒），
  我们的时基会把整段判成"向上跳"→ **整段时间丢掉 → 屏上的钟倒退**。

所以睡眠版的**前提**是：时基必须先从这个定时器上搬走。

### ③ 方案（四步，每步都能单独刷机验证 + 一键回退）

| 步 | 做什么 | 为什么这么排 |
|---|---|---|
| **1** | **时基搬家**：不用 AON 睡眠定时器，改用 **AON 日历/RTC**（`hal_calendar_*`，AON 域里有完整的年月日时分秒 + 毫秒 + 闹钟） | 一石四鸟：① 不再跟 SDK 抢睡眠定时器；② "现在几点"变成**读寄存器**，换天/每分钟/报 `t=` 都不用再靠累加；③ AON 域有电就不丢，**跨软复位、跨刷固件都还在**（顺手解决 backlog 第 15 条的前半段）；④ 它的**闹钟能当唤醒源**，正好是第 4 步长睡要用的 |
| **2** | **把暖启动这条路接回来**：`main_init()` 按 `pwr_mgmt_get_wakeup_flag()` 分支；**加保险** —— RAM 里没有"我真的睡过"的魔数就退回冷启动（魔数由 `app_prepare_for_sleep` 回调在睡下去前写） | 万一那个 flag 在"从 bootloader 跳进来"时也报暖启动，有保险就不会变砖 |
| **3** | 打开 `PMR_MGMT_SLEEP_MODE`，并注册 `app_prepare_for_sleep` —— **正在刷屏（16~18 秒）时拒睡** | 刷屏是长时间阻塞，中间被睡下去会把屏刷坏 |
| **4** | 长睡：用日历闹钟睡到"下一个要干活的时刻"（整分/换天/下一次天气） | 这才是 CR2450 想要的那种省电 |

**本轮只做了"探路"**：给 `status.sh` 加了一段**纯只读**的探针（不需要刷机），
把决策要看的两件事直接印出来：

* `AON 日历/RTC（CALENDAR_TIMER_CTL）`：EN / CLK_SEL / WRAP_CNT / 中断使能 ——
  看那颗硬件 RTC 现在是不是空着的（EN=0 = 没人用，可以拿过来）；
* `PWR_RET01 的 WAKE_UP_SEL`：现在允许哪些唤醒源（SLEEP_TIMER / BLE / CALENDAR / …）——
  第 4 步要加的 `CALENDAR` 就在这个字段里（`AON_PWR_REG01_WAKE_UP_SEL_CALENDAR`）。

拿这两个读数 + `pwr_mgmt_get_wakeup_flag()` 的行为，就能定第 1、2 步的具体做法。

### 探针实测（2026-10-04 18:38 的 status，build 77）

```
AON 日历/RTC（CALENDAR_TIMER_CTL = 0x00003100）:
   EN=0   CLK_SEL=1   WRAP_CNT=0   闹钟中断=开   回绕中断=开
   → 日历没在跑（EN=0）—— 这颗价签上现在没人用它。
PWR_RET01 的 WAKE_UP_SEL = 0x05  → 允许的唤醒源：SLEEP_TIMER/BLE
AON TIMER_VALUE（装载暂存）= 816874    （816874 ÷ 27230 = 29.99 秒）
AON_PAD_CTL1 = 0x800000FF   TIMER_READ_SEL = 2 → SLP_TIMER
```

三条结论：

1. **日历是空着的**（`EN=0`）—— 可以拿过来当我们的时基，第 1 步可行。
   顺带注意：`ALARM_INT_EN/WRAP_INT_EN` 已经是 1（默认值），所以启动它之后
   那两个中断标志会置位；`CALENDAR_IRQn`（33）没使能，不会跑 ISR，但别被标志骗了。
2. **`TIMER_VALUE = 816874`（29.99 秒）** —— 这是**直接证据**：SDK 的 app_timer
   刚把睡眠定时器按"下一次到期"装过。跟我们前两轮从日志算出来的
   "30.00 秒 / 24.00 秒的固定装载值"是同一件事。
3. **`WAKE_UP_SEL = 0x05`（SLEEP_TIMER | BLE）** —— 现在只有这两个能唤醒芯片。
   第 4 步长睡要用的 `CALENDAR` 位（0x08）就在这个字段里，加进去即可。

### 第 1 步待确认的一件事：**日历的走时精度**

日历计数器跑在低功耗时钟上（`CLK_SEL` 选的那一档），而这颗价签**没有 32.768k 晶振**，
走的是内部 RC —— 我们开机用 DWT 标定出来是 **27230 Hz**（标称 32768 的 **83%**）。

如果 HAL 内部按"标称 32768"去折算计数器→秒，那 RTC 会**每天慢约 4 小时**，
拿它当钟就废了；如果它用的是 `sys_lpclk_get()`/标定值，那就没问题。
`drivers/src/` 里没有 calendar 的源码（在 `libble_sdk.a` 里），头文件也没写清 ——
**只能实测**：

* 让 RTC 跑起来、写进基站给的时间；
* 同时记录"RTC 读回来的时间"和"我们现有 tick 推出来的时间"，两者都进状态块；
* 隔 10 分钟再读一次，看 RTC 走了多少秒 —— 走对了说明它用的是标定频率，
  慢 17% 说明它按标称 32768 折算，那我们就得自己换算（或者把 RTC 只当"计数器"用，
  拿我们标定好的 27230 Hz 去折算）。

## 12. 换方向：价签当「哑终端」（2026-10-04 深夜，用户拍板）

用户的关键一问：**"价签因为有基站，只要被动接受推送就行，天气/温度/变天都能从
基站推下来 —— 这样省电能不能走更宽的路？"**

**答案：能，而且这才是这颗芯片该走的路 —— 原厂就是这么干的**（第 8 节逆出来的：
唤醒间隔由基站下发，找不到 AP 才顶到 30000 秒）。更关键的是：**哑终端模式下
价签根本不需要读 AON 睡眠定时器**，于是"跟 SDK 抢定时器"这个死结自动消失，
日历也不需要了。用户明确拍板：**屏上不需要一直准的钟**。

### 账（这是选这条路的唯一依据）

| 项 | 每次/每天 | 折算 |
|---|---|---|
| 一次**整屏刷新**（16~18 秒） | —— | ≈ **0.067 mAh/次** |
| 一次**醒来窗口**（12 秒广播 + 等连接） | —— | ≈ **0.010 mAh/次** |
| 睡 15 分钟一轮（96 次/天） | 0.96 mAh/天 | ≈ 1.7 年 |
| 睡 30 分钟一轮（48 次/天） | 0.24 mAh/天 | ≈ 6 年（先撞自放电） |
| 真刷屏 4 次/天 | 0.27 mAh/天 | ≈ 6 年 |
| 睡眠电流 | 待实测 | 决定天花板 |

**结论：窗口是主要开销，刷屏是次要开销 —— 所以"睡得久"比"刷得少"更重要**，
但两者都要压：走 **醒 12 秒 / 睡 30 分钟 / 真刷屏 2~4 次每天**，粗算 ≈ 0.5 mAh/天
→ **约 3 年**。

### 实施（5 步，第一版只做 1~4 的"睡眠 + 窗口"部分）

1. **时基降级**：不再读 `AON->TIMER_VAL`（回到 CYCCNT，只给 BLE 超时/限速用，
   精度不重要）—— 这一步就把"SDK 每 5ms 重装定时器 → 我们的钟不走"那个坑删掉；
2. **删掉"自己会走"的逻辑**：换天 / 每分钟重画不再由价签判断，**只认命令**
   （日历页画的就是推送那一刻的日期）；
3. **醒来窗口**：`ble_gap_adv_start` 带 **duration = 12 秒**，窗口一过自动停广播；
   窗口里广播间隔用 **30ms**（不要放宽 —— 只有 12 秒，得让基站尽快抓到）；
4. **睡多久**：一个 `app_timer`（30 分钟）当"下次醒来" + `PMR_MGMT_SLEEP_MODE`；
5. **刷屏时不睡**：`app_prepare_for_sleep` 里拒睡。

### 已经就位、这条路会用到的资产（不白做）

* **暖启动通路（build 80/81）**：哑终端一样要睡，一样会暖启动 —— 这块是必需的；
* **魔数保险**；**睡/醒回调注册 + 补时间（build 82/83）**：补时间以后用不上，
  但回调注册那套（`pwr_register_sleep_cb`）正好是第 5 步"拒睡"要用的骨架；
* **`t=` 主动回报**：窗口里基站一连上就知道"你是不是刚醒/刚上电"，
  判断"这次要不要整包推"仍然有用；
* **诊断脚本**（状态块 118~133 那一批探针）：实机验证全靠它。

### 明确的取舍（说清楚，别再当惊喜）

* 基站不在（关机/断网）时，屏上停在上次推的内容：**时间会旧、天气会旧，但不会乱**；
  原厂同样如此（找不到 AP 就顶到 30000 秒）。
* 想再省：把睡眠放到 60 分钟（代价：基站想推东西最多等一小时）。
* 想"屏上一直有准的钟"：那就得回到"时基搬家"那条路（第 11 节），
  属于另一个量级的活儿 —— 用户已明确：**不要**。

* A 组（纯日历）：3 天推 4 次（刚出现 1 + 跨天 3），**跨天那次都落在本地 0 点**，
  **没有任何一天推超过一次**，相邻间隔 = 50400 / 86400 / 86400 秒；
* B 组（对照组，没关天气）：一天推 6 次、第一个间隔正好 21600 秒 ——
  证明 A 组的判据**真能抓住"每 6 小时白刷"这种退化**，不是自我安慰。

**③ ESP32 基站**（`esp32/zk_base_esp32/zk_base_esp32.ino`）：新增 `#define WX_SEND_ENABLE 0`。
* 0 = 不写 0x71、0x20 也不带天气字段、预警一并关掉（`alertLevelNow()` 归 0）→ 纯日历；
* 1 = 老行为。
⚠ **那次 HTTP 取数没省**：这台板子的"现在几点"就是从这次请求的 **HTTP Date 响应头**来的

想连取数也省掉得换时间源（NTP/RTC），那是另一件事，先不动。

## 15. build 89：**内部计时修准**（用户："时钟用回之前的准的，这样就不用基站了"）+ 值没变不重画

**用户原话**："时钟用回之前的准的，这样就不用基站了。**不是界面显示时钟，是内部计时**。"
（意思：价签自己的单调时基要准到能**自己**在 0 点翻页 —— 不靠基站每天推那一下。）

### ① 先拿证据：哪一版准、哪一版不准（把 outputs/pyocd 里所有 status 日志拉成一张表）

| 配置 | build | `时基实测` 比值 |
|---|---|---|
| AON 时基 + 主循环忙等（`ZK_PWR_SAVE=0`，**没有 app_timer**） | 59~83 | **0.994 ~ 1.000** ✅（20 份日志） |
| AON 时基 + IDLE + **500ms app_timer**（`ZK_PWR_SAVE=1`） | 85~87 | **0.885 / 0.896 / 0.902 / 0.908 / 0.929** ❌（5 份） |

0.9 就是**一天慢 2.4 小时**，"0 点翻页"会跑到凌晨 2 点多，所以用户说它不准。
两边时基代码是同一份、频率标定也一样，**唯一差别是睡眠定时器被"重装"的频率**
（app_timer 每 500ms 重装一次；没有 app_timer 时只有 PMU 校准每 30 秒一次）。

### ② 根因：重装一次，就吃掉"上次读数 → 掉到 0"那一段

AON 睡眠定时器是**递减**计数器，数到 0 被 SDK 重装（raw 从 0 跳回装载值）。
老代码（`zk_tick_aon_step`）在归一化后看到"往上跳 ≥2^31"，只 `bad++` 就完了 ——
于是那一段**整段被丢掉**。主循环在 IDLE 下 ~20Hz（50ms 一圈），
每 500ms 丢 ~25ms ≈ 5%，再加协议栈/PMU 校准自己的重装，正好是实测那 7~11%。

**离线自测把这件事钉死了**（`tools/test_tick.py` 第 12 条，喂的就是本机参数
hz=27216、装载值 13608（=500ms）、每 50ms 读一次、跑 100 秒 = 200 次重装）：

| 喂同一段轨迹 | 走了多少毫秒（真值 100000） | 偏差 |
|---|---|---|
| 老函数 `zk_tick_aon_step()` | **90048** | **−10.0%**（跟现场 0.885~0.929 完全对得上） |
| 新函数 `zk_tick_slp_step()` | **100000** | **0** |

### ③ 修法（build 89，两处）

1. `Src/board/zk_tick.h` 新增 `zk_tick_slp_step()`：raw 往上跳 = 重装过 →
   补两段：**上次读数掉到 0**（= `t->last` 个 tick，就是以前丢掉的那段）
   + **重装后走到现在**（`load - raw`）。只对递减计数器生效（本机就是递减；
   递增那条路继续走老函数）。
   * `bad` 这个字段的含义跟着改了：现在是"**补记过几次重装**"（诊断用），不再是"异常"。
   * ⚠ 主循环被长时间堵住（刷屏 16 秒里有几十次重装）时**只能补一次** ——
     那一段会少算 ≈15 秒/天 ≈ **0.02%**（≈ 6 分钟/年）。认了，理由见第 14 节。
     自测第 13 条专门盯这条："不许往前跳、不许崩"。
2. `Src/main.c` 读 AON 计数器前**先把 `AON_PAD_CTL1` 的 TIMER_READ_SEL 拨回
   睡眠定时器**（跟 SDK 的 `ll_calendar_get_counter()` / `ll_aon_wdt_get_counter()`
   一个做法，整段关中断）—— 免得别的代码把选择子挪走、我们读到另一个计数器。
   顺便多一个 `tb_aon_load()` 读装载暂存（重装后那一段要用它）。

### ④ 第二件事：**值没变就不重画**（不然"自己跳"和"基站推"会变成一天两次全刷）

价签自己 0 点翻页刷一屏；基站 0 点那轮还会把**一模一样**的东西重发一遍
（时间 + 城市名 + 休/班表 + 节日名 + 纪念日），以前每一条都会 `gui_request_redraw()`
→ **同一天刷两次**。现在：

| 命令 | 以前 | 现在 |
|---|---|---|
| `0x20` 只对表（mode=0）+ 日历页 + 没带天气 | 必刷 | **算出来的日期跟"画过的那天"一样就不刷**（时钟页不适用，那里要对时分） |
| `0x79` 城市名 | 必刷 | 跟存着的一样就不刷 |
| `0x7E` 休/班表 | 必刷 | 年/月/8 字节表一样就不刷 |
| `0x7F` 节日名 | 必刷 | 日子+名字一样就不刷 |
| `0x7A/0x7B` 纪念日 | 必刷 | 攒齐后在 poll 里跟"画上去的那版"比，一样就不刷 |

**结论**：开不开基站，对价签都只有 0 点那**一次**全刷；基站那轮变成一次**空连接**

### ⑤ 顺便回答"基站每天发 vs 自己准时钟跳，哪种更省电"

⚠ 广播那两行是**按射频占空比估的，没实测**（电流一直没量过），只用来排序。

* 至少要**同步一次时间**（手机网页点一下）才走；**换电池后要再同步一次** ——

### 0.45% 是什么：**"数到 0 → SDK 重新装好"之间那段死时间**

算一下就知道：`1.37 秒 ÷ (1.91 次/秒 × 305 秒) = 2.35 毫秒/次` ——
也就是说**每重装一次，计数器在 0 上停 2.35ms 不数了**（中断延迟 + SDK 算下一个到期点 +
把装载值写回去）。500ms 一档里丢 2.35ms = 0.47%，2 次/秒 ⇒ 0.45%/秒 ✓ 跟实测对上。

⚠ 这段死时间**硬件本身没数**，所以我们没法"读出来补上"—— 只能**少重装几次**。

### 修法：节拍 500ms → 2000ms（重装少 4 倍）

| app_timer 周期 | 重装频率 | 每天慢 |
|---|---|---|
| 500ms（build 85~90） | 2 次/秒 | **406 秒 = 6.8 分钟** |
| **2000ms（build 91）** | 0.5 次/秒 | **102 秒 = 1.7 分钟** |
| 5000ms（还能再放） | 0.2 次/秒 | 41 秒 = 0.7 分钟 |

主循环不需要"勤"：连着的时候协议栈自己的事件（连接间隔几十 ms）本来就会把它叫醒；
这个节拍只是"什么都发生时也保证每 2 秒转一圈"（窗口调度、到点重画检查都是秒级以上）。

warm boot 的 `boot_count = 2` 对照）。固件里除了命令 `0x91`（没人发过）没有任何复位路径，
AON 看门狗也是关的（`WDT CTRL = 0`）。

**所以 build 93 干一件事：把"复位现场"记下来。**
`AON->SLP_EVENT` 这个寄存器里有 BOD_FEDGE（**掉电**）/ EXT（外部脚，比如按 RST）/
WDT / TIMER / BLE 等位，但它会在 `soc_init() → platform_init()` 里被
`ll_pwr_clear_wakeup_event(ALL)` 清掉 —— 而我们的 `main_init()` 比 soc_init 早，
所以在最开头抄一份（外加 `AON->PWR_RET01`）存进状态块两个新字（138/139），
`status.sh` 会译成"是掉电、还是被按了 RST、还是普通上电"。

**下一次它再重启，第一眼就能定性**：
* 置了 BOD 位 → **电池供电抖了**（CR2450 内阻 + 刷屏/射频脉冲电流，或者电池夹接触不好）
  → 换新电池 / 检查夹子 / （硬件）并一颗大电容；
* 全是 0 → 普通上电或软复位，那就要从别处查（谁在拉低 RST？）。

**顺带说清影响**：这种重启**不会让屏乱**（墨水屏留着旧画面），而且基站每 9 秒扫一轮、
价签开机又有 5 分钟窗口，所以基站会在几秒内发现它并把时间/内容重推一次（代价：白刷一屏
≈0.067 mAh）。但"独立跑"这件事会因此变脆 —— **每次重启都要重新对表**。
所以这个重启在"省电/独立运行"这条线上，比那 0.3% 的走时误差重要得多。

镜像：build 93，`bin_size 0x23ED8(147160)` / `check_sum 0x00DE453D` / 37 颗扇区 /

`ZK_DBG_WORDS`，正是它该干的事）。

### ① 判别实验（build 94，`ZK_TICK_MS` 2000 → 200）

| 那次 | 节拍 | 重装率 | 长阻塞补记 | 时基实测（全量） |
|---|---|---|---|---|

不是低频 RC 睡着变慢。剩下的 1.6% 正好对上"每次重装 ~2.35ms 死时间 × 5 次/秒"。
两条路都不香：**省电就要接受 6.7%，要准就得多 10 倍唤醒** ⇒ 节拍改回 2000ms，

### ② build 95：AON 日历计数器探针（**这条路 2026-10-04 走过、当时判定"没用起来"**）

当时（build 78/79）失败的原因，对着 SDK 才看清：

| 当时的做法 | SDK 的正确姿势（`drivers/src/app_rtc.c`） |
|---|---|
| `ll_calendar_reload_counter(0)` **装 0** | 装 0 是退化情况（装完还是 0）→ 用 `hal_calendar_init_time()` |
| 只置 `EN=1`，没管分频 | `hal_calendar_init()`（内部设 `CLK_SEL`：1/32、1/64… 见 `ll_calendar_set_clock_div`） |
| 自己摸寄存器换算 | `hal_calendar_get_time()` + `ll_calendar_get_counter()`；GR551x 路径还配 `pwr_mgmt_wakeup_source_setup(PWR_WKUP_COND_CALENDAR)` |

而且 `app_rtc.c` 里有两条关键线索：日历**能当唤醒源**（说明它在睡眠时继续数），
以及 `calendar_time_sync` **每 23 小时要调一次**（32 位计数器 ~27kHz 下 36 小时绕一圈）
—— 也就是它就是个"自由跑、没人重装"的慢时钟计数器，正是我们缺的那块。

**build 95 只探路**（时基一个字不改）：`hal_calendar_deinit/init/init_time` 正规初始化 +
装 2026-10-15 00:00:00 + 关掉它的事件，然后每 ≥1 秒读一次原始计数与 HAL 换算的秒，
把**实测速率（Hz×1000，跨着睡眠量的）**写进状态块 140 号字、HAL 的"当天第几秒"写进 141。

判据：`≈27235` = 慢时钟直出（最理想，直接搬时基）；`≈851` = 1/32 分频（也能用）；
**明显更小 = 睡着时它不数 ⇒ 这条路也废**。那个"跨着睡眠量"是关键 ——
主循环 2 秒才醒一次，所以速率里天然包含睡眠时段。

镜像：build 95，`bin_size` **0x249A0 = 149920 字节**（上限 151488，**只剩 1568 字节** ⚠ ——

### ⑤ build 97：**把"睡着时到底给了多少 tick"直接量出来**（决定 6.7% 是记账还是时钟）

现在有两组互相矛盾的证据：

| 证据 | 说明 |
|---|---|
| 宿主量到的 `约 27233 Hz` | 但那是**调试器把 CPU 停住**（= 醒着）时量的 |
| 长期走时（79 分钟慢 6.7%） | 反推"睡着时"只有 ~25.5 kHz |

"睡着时到底多少"只有固件自己数得出来，于是 build 97 在**睡眠定时器到期中断**里
（`SLPTIMER_IRQHandler`，顶掉 app_timer.c 那个 `__WEAK` 版本；**必须在 SDK 之前读**，
因为它马上会把 `AON->TIMER_VALUE` 改成 `0xFFFFFFFF` 待命）把"这次到期消耗的装载值"
累加进状态块（142 = 到期次数、143 = 累计装载值），最后再调
`hal_pwr_sleep_timer_irq_handler()` 把活交回 SDK。

`status.sh` 新增一段"睡眠节拍实测"（5 秒窗口）：**Δ累计装载值 ÷ Δ主机秒**：
* ≈27235 → 睡着时 tick 也给够了 ⇒ 那 6.7% 是**我们的记账**丢的，纯软件能修 ✅；
* 明显更小（~25.5k）→ **tick 本身就来得慢**（时钟变慢 or 有一段停着）⇒ 按实测值
  重新标定，或者把"停着那段"单独补上。

这个数**一次把两个嫌疑都涵盖**（它把"被装成 0xFFFFFFFF 待命、等主循环来重装"那段
也算了进去）—— 而且它同时是"在中断里记账"的骨架：真要在 ISR 里补时间，就靠这个钩子。

镜像：build 97，`bin_size 0x24A28 = 150056`（⚠ 只剩 **1432** 字节）、
`check_sum 0x00E3271D`、SHA-256 `eaedef64…`；13 套自测全绿。

* 不需要"省电/常电"两套方案（没有额外的刷新要省）；

所以 build 99（编译期两套）和 build 100（运行时 `0x74` 切换）**都撤掉**，价签回到

### 基站侧

* **Mac**（`zk_ble_base.py`）：`fetch_daily_any()`（中继 / 和风 3d / Open-Meteo daily
  三条路）；**实况 0x71 默认不发了**（`--wx-live` 是留给调试的后门）——
  实况一天变好几次、一变就整屏刷 16 秒，那正是这一轮要砍的开销；
  当天天气**值变了才发**（`daily_key()`：日期也进 key ⇒ **跨天必发**，0 点那轮靠它）。
  中继那份 JSON 一轮只问一次（`_relay_json`，实况/当天/预警共用）。
* **ESP32**（`zk_base_esp32.ino`）：`WX_DAILY_ENABLE 1`（跟老开关 `WX_SEND_ENABLE`
  =实况 分开）；解析中继的 `day/night/tmin/tmax`；中继没答上来时用**同一次**
  Open-Meteo 请求里的 `daily=weather_code,temperature_2m_max,temperature_2m_min`；
  发 `0x74`（5 字节），跨天靠 `dailyKeyNow()` 里的日期。
