## 2. 为什么算一个里程碑（之前 vs 现在）

**之前**：日历页的"现在几点"是 `CYCCNT / 16000` 算出来的，而 CYCCNT 数的是 **CPU 周期**。
GR5513 空闲时主频 16 MHz、刷屏/连 BLE 时高得多，于是这个"毫秒"平均**快 3~4.8 倍** ——
用户看到的表现是"9-30 晚上就显示 10 月 1 号"（每 ~8 小时跨一天）。
更坑的是它**看起来是对的**：`status.sh` 自检（空闲那一下）读到 16 MHz 分毫不差。

**现在**：时基跑在 **AON 定时器**上（低功耗时钟域，与 CPU 主频无关，实测 ~28 kHz 且**递减**），
频率开机标定一次并跟 SDK 的值交叉核对；所有"定时重画/换天/换分钟"的逻辑都走它。

**证据链**（都在 `outputs/pyocd/status-*.log` 与本文档）：

```
build 58 的观测量：一次 d = 1e9 个周期 —— 按 16 MHz 算成 62 秒，而真实只过了 20.8 秒
                    （正好一次全刷）⇒ 比值 3.0，且证明"主频确实会变"
改完（build 59）实测：价签 5.00 秒 / 真实 5.01 秒 ⇒ 0.999
                      价签 5.01 秒 / 真实 5.01 秒 ⇒ 1.000
                      flags = 0x2C ⇒ 含 0x20 = 确实在跑 AON 时基（不是回退）
```

## 3. 怎么复现验收（刷完必做）

```bash
cd /Users/mac/Documents/Codex/2026-09-15/a/outputs/pyocd
MODE=app bash flash-app.sh                     # 刷 build 60
STATUS_SETTLE_MS=0 bash status.sh | grep -A8 "时基实测"
```

* 判据一：**`价签走了 X 秒 / 真实 Y 秒 ⇒ 比值 ≈ 1.00`**（修之前 3~4.8）。
* 判据二：那一段上面的「毫秒时基」会印 `来源 / 频率 / 标定值 / SDK 值 / 异常次数`。
* 判据三（build 60 新增）：`校时命令 0x20：一共 N 条，其中 M 条是「只对表、不动页面」` ——
  M 会随着基站每次推天气往上走，说明"推天气顺手带时间"这条真的在跑。
* 判据四（要等真实时间）：**日历在真实 00:00 才换天**（挂过零点即可确认）。

## 4. 已知取舍 / 还没做的

| 事 | 现状 |
|---|---|
| 屏上表头那个**时分** | 只在每次推送那一刻是对的 —— 日历页只在「换天/收到命令」时重画。想更勤：ESP32 `PUSH_EVERY_MS`（每 15 分钟一次全刷）或切时钟模式（每分钟一次全刷，1440 次/天） |
| **局刷**（便宜地刷新小块） | 仍判定"可行但暂不做"：`0xD7 + 短延时` 是快刷，但整屏用必发灰；社区那个"校准局刷参数"是别人固件的私有命令 |
| 时间/模式**持久化**（装电池就显示日历） | 没做：时间还在 RAM，掉电就没了。候选扇区 `0x0107E000`（**绝不碰** `0x0107F000` 的 NVDS） |
| `epd_delay_us()/epd_delay_ms()` | 仍按 CYCCNT 折算（本次**故意没动**：它只影响 SPI 时序和 BUSY 轮询，改了要重新校面板时序）。`epd_wait_busy` 的 30 秒超时数的是 200µs 步数，不受时基改动影响 |
| 时钟模式的刷新节奏 | 现在每分钟一次全刷（照原厂）。要真当天钟用，得等局刷 |
